## 0. 一页结论

**这是一套"跑得起来、但已经静默坏掉一部分"的单机系统。** 它最突出的优点和最致命的问题来自同一个特征：**大量正确性依赖"文档与人的记忆"，而不是机器可验证的门禁**。

三句话概括这一轮：

1. **数据层已经破了，且系统自己不知道。** 现网库 `translations_fts` = **0 行**，而 `translations` = **3532 行**，其中 **3532 条（100%）的 `segment_id` 悬空**。结果是：**译文（目标语言）索引为空——翻译成果本身搜不到**；默认的中文查询会被 LLM 改写成英文去命中原文，所以"有时看起来能用"，代价是每次检索先付一次改写费（见 §4.3）。唯一的重建入口在当前数据上必然产出 0 行。**这是本轮唯一的 blocker，并且是"假成功"型缺陷**——没有任何报错，用户只会觉得"搜索不好用"。
2. **测试全绿掩盖了真实风险。** `npm test` 155 pass / 0 fail / 0.9s 看着很漂亮，但 77 个服务端模块里 **27 个零覆盖、27 个只有间接覆盖**；启动链、全部 HTTP 路由、安全中间件、下载器网络段、LLM 客户端、翻译批处理**一条直测都没有**。更严重的是：**测试会直接写生产库与生产附件库**（A15 F1），所以"跑一下测试"本身是危险动作。
3. **工程门禁整体缺失，是"贵"的根源。** 无 git、无 CI、无 lint、无覆盖率工具；`FREEZE.md` 哈希清单 **v5 的 13 行里 4 行漂移**（全表 105 行按 A03 计 35 行，未独立复核），且它引用的两份 E2E 脚本其实还在（原报告看错目录，见 §4.3）；README 说 69 个用例（实际 155）、说 schema v1（实际 v4）。没有门禁 ⇒ 上一轮修好的 6 个 bug 没有一个留下会失败的测试 ⇒ 下一轮还会坏。

**但也要说清亮点**（这些不该在优化中被破坏）：

- 入站安全做得扎实：Host 白名单、写接口 Origin 校验、JSON 强制，实测恶意网页发起写请求**不可行**、DNS rebinding 被 Host 白名单挡住。
- 路径白名单 **12 组绕过测试 0 漏**；出站 SSRF **13 组 0 漏**（十进制/十六进制/短写/IPv6 映射/nip.io 全拦）——只差"IP 钉扎"与"端口白名单"两处收口。
- **300 条内部 import 边、0 循环依赖**、153 处设计文档章节引用、**0 处悬空引用**：这套代码对"设计—实现"的可追溯性远高于它的工程门禁水平。
- 只有 2 个直接依赖（express、pdfjs-dist），`node:sqlite` 内置——**依赖面极小是这份代码最大的长期资产**。

**建议的落地节奏**（详见 §5）：先修"数据可信 + 可观测"（P0），再补"AI 链路可验证"（P1），然后"性能与结构"（P2），最后"文档与门禁"（P3，但第 1 天就该开工）。

## 2. 整体架构、模块职责与依赖关系

### 2.1 分层与职责（实际形态）

```
浏览器（零构建原生 JS：index / work / settings / reader + 9 个 assets/*.js）
   │  fetch / SSE / pdf.js（vendor 内联）
   ▼

   │
   ├─ routes/ (11)      参数校验、状态码、序列化        ← 46 处路由注册
   ├─ middleware/       security / validate / error / ratelimit
   ├─ services/         业务：artworks importer storage downloader extractor fts

   ├─ db.js             node:sqlite 薄封装（exec/all/get/run/tx + WAL）
```

**分层总体成立**：`routes → services → db` 是主方向，300 条内部 import 边里 **0 条循环**。95 个服务端模块，扇入最高 `config.js 41` / `db.js 31` / `errors.js 29`，扇出最高 `app.js 15`。

### 2.3 启动链与隐式顺序依赖（一个真实的坑）

`03-code/server/index.js:21-24` 的实际顺序：

```js
openDb(cfg.server.dbPath);
const mig = migrate();          // ← 迁移在这里跑
applyDbSettings(all);           // ← DB 设置（含翻译引擎）在这里才生效
ensureDirs();
```

`migrate()` 内部会按"当前翻译引擎"清空并回填译文索引，而它读到的引擎来自 **config 文件（deepseek）**；`applyDbSettings()` 之后才变成 **settings 表里的 qwen**。实测 A/B 确认了这次错配，而迁移里的断言用同一个错值自比自，**永远通过**。→ F1-02。

## 4. 结论可靠性：8 条断言的对抗式裁决 + 我本人的独立复核

15 个评审代理是同一后端、同一批上下文里长大的，**共享盲区是真实风险**。所以另起两个代理，只给"待验证断言"、不给报告，要求它们自己重跑证据，并对"成立 / 不成立 / 成立但被夸大"表态。它们**没有让所有结论原样通过**：8 条里 **成立 5 · 成立但被夸大 2 · 部分成立 1 · 不成立 0**，其中 2 条改掉了清单措辞、1 条降了 severity、1 条删掉了一个错误事实。

### 5.0 怎么读这张清单

### 5.5 明确**不要**做的事（反优化清单）

这一节和上面同等重要——评审里有些"看起来该做"的事，实测/推演下来是负收益：

1. **不要加 gzip/`compression`。** 本机回环传 1.29MB 只花 3.9ms，而 gzip 10 个文件要 **41.8ms CPU**、brotli q11 要 **2655ms**——净亏，且 304 已生效。首屏 2046KB 是真的，但解决方向是"vendor 加 `maxAge:365d immutable`"，不是压缩。
2. **不要在没有 git/CI 之前做 P2-8、P2-11 这类结构性重构。** 现在改坏了无法回滚、无法归因（35 个 FREEZE 漂移文件已证明）。
3. **不要在 P3 视觉通道（`lit_page_image`，约 1060 行）上投入"接通"工作。** playwright 未装、前端零引用、`enabled` 默认 false。要么明确**冻结并移出主链**，要么整块删；先做决策，别做半成品。
4. **不要引入 TypeScript / 构建工具 / 前端框架。** "零构建原生 JS + 2 个直接依赖"是这份代码**最大的长期资产**（A04/A03 均确认依赖面极小、入站安全扎实）。结构化风险应该用**测试与机检**解决，不是用框架。
5. **不要用 `npm audit` 当门禁。** registry 404，跑不起来；改为锁定精确版本 + `freeze:check`。
6. **不要扩大直接依赖数。** 需要 `supertest` 的地方用 `node:http` + `fetch`（A15 建议的 90 行 http smoke 就够）。
7. **不要为了"性能"去优化启动时间。** 173.7ms 里 117.6ms 是模块图加载（`import app.js` 占 68%），在单机自用场景**不是瓶颈**；要做的只是**加阶段计时**（6 个毫秒字段），让下次变慢时看得见。

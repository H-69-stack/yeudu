### 0.3 Q2 能力契约：边界是"**分辨率上界**"，且 token 成本随面积线性到顶（v3 修正）

§1bis 之后不再有"只能看扫描页"的限制；剩下的硬上界可算清：

> **provider 每图 ≤1024 vision tokens；1 token 格 = 14px patch × 3 = 42px（对送入的图）。**
> ⇒ 细节上限 = 42 源像素/格；能覆盖的格数 ≈ 1024 ⇒ **约 1.73 Mpx 的图像面积是"有效像素预算"**。

**修正 v2 的一处说法**：我此前写"token 成本恒定 1010"——那只在上限附近成立。精确式：

```
tokens ≈ cells(w) × (cells(h) + 1) + 2 ，cells(p) = ceil(floor(p/14)/3)
       ⇒ tokens 随面积线性增长，封顶 1024
```

复算（对接 §7 的两档）：

| 档位 | 尺寸 | token 网格 | tokens | 每格源像素 | 字节（JPEG q0.85） | 实测可读性（§7） |
|---|---|---|---|---|---|---|
| §7 低档 = scale 1.0 | 570×759 | 14×19 | **306** | 40.7 | 108 KB | **主标题正确**（`Software Agents`） |
| §7 高档 = scale 2.0 | 1140×1518 | 27×36 | **1010** | 42.2 | 335 KB | 主标题 + 页眉（`INTELLIGENT AGENTS`） |
| **本设计默认**（长边 1500） | 1126×1500 | 27×36 | **1010** | 41.7 | 329 KB | ≈ 高端档（1.98×） |
| 1/4 象限（长边 1500 铺满） | 1126×1500 | 27×36 | 1010 | **20.9** | 156 KB | 未实测（应更清晰） |

三条由此确定的结论：
1. **token 与细节是"面积"上的同一个旋钮**：面积 ↑ ⇒ tokens ↑（线性到顶）且细节 ↑。所以"缩到 570 宽省 2/3 token"是真的省，代价是细节按面积等比下降——§7 证明大字号（标题）在这个档位仍可读。
2. **裁剪是唯一"不加钱换清晰"的杠杆**：1/4 象限铺满同长边 ⇒ 同 1010 tokens、每格 42→20.9 源像素（2 倍精细）、字节反降到 1/2、耗时降到 1/3。默认档保留 `maxEdge=1500` 而**不是**更低，正是因为它落在 §7 实测的"能读标题+页眉"档；想省 token 的模型可以自己传 `maxEdge=800`。
3. **扫描页的物理天花板由扫描 DPI 决定**（`1.17` 的内嵌图 1579×2106 ≈ A4 200 DPI）；`region` 放大到 20.9 px/格时已接近该扫描的物理极限，再放大只是插值 —— `guidance` 必须写明。

**契约形态**：
- `status: 'ok'`：图已注入 + 尺寸/区域/pageCount/缩放元数据 + 分辨率说明 + "看更小区域用 region"的指令。
- `status: 'no_pdf'`：本地无 PDF ⇒ 去 `lit_search`。业务状态，不抛错。
- **环境/协议故障一律 throw**（浏览器未装、launch 失败、渲染超时、page 崩溃、页码越界、pdf.js 资源缺失），**禁止**降级成任何 status（§18-2）。
- **区域是几何概念，不是枚举**（v3.1）：契约的原生表达是归一化矩形 `[x0,y0,x1,y1]`（0–1，相对整页），`region` 的 5 个名字只是**预设**（`full` / 四象限）。所以"更细的网格"不用改接口——传一个 0.25 宽的 `rect` 即可；但也**不把 16 块做成枚举**（实测收益不成立，见修订记录 v3.1-1）。
- **成本闸是一次数闸，不是 token 闸**（v3.1）：每图 306–1010 tokens 是唯一按次线性增长的成本项，故闸门开在"每会话调用次数"上，由 `ctx.pageImageUsage`（会话日志投影）计数——**不是进程内变量**，插件重载/进程重启后从日志恢复，不清零（§4.4、§8.2-B）。
- 多页：**一次一页**（§17-6）。
- 体积：默认档实测 ≤335 KB，远低于 `normalizedImageMaxBytes`（4 MB，`attachment-local/src/index.ts:58`）与 `maxImageBytes`（50 MB）⇒ 无需额外预算机制；探针继续打印字节做回归。

### 0.4 Q3 接口设计：`lit_page_image`

**命名理由（v3 重写）**：叫 `lit_page_image` 而**不叫** `lit_render_page`，与"本机有没有渲染引擎"无关（那已是过时判断）。理由是**契约命名**：这个工具承诺的是"产出第 N 页的图像"这一**契约**，实现用 Chromium、内嵌位图、远程渲染服务都不改变契约；名字跟着契约走，将来换实现不用改名、不用改 prompt。反过来 `render` 把实现细节写进了名字，且暗示"我按你的 dpi 渲染"——而实际参数是 token 预算导向的 `maxEdge`。

参数（`ParameterSchemaSpec`，`packages/core/tools/src/schema.ts:555`；`type` 必填）：

```ts
{
  no:      { type: 'string',  required: true,  description: '文献编号，例如 "1.17"' },
  pageNo:  { type: 'integer', required: true,  description: '页码，从 1 开始（pageCount 可先由 lit_read 取得）' },
  region:  { type: 'string', enum: ['full','top-left','top-right','bottom-left','bottom-right'],
             description: '只产出页面的一部分（默认 full）。看小字时用它：同样的 token 成本，分辨率约提高 2 倍' },
  rect:    { type: 'array', items: { type: 'number' },
             description: '自定义区域 [x0,y0,x1,y1]（0–1 小数，相对整页，需 x0<x1、y0<y1），与 region 互斥；比 region 更细的粒度用它' },
  maxEdge: { type: 'integer', description: '输出图像长边像素上限，默认 1500（夹取到 600–2048）。调小可省 token（细节按面积等比下降）' },
  format:  { type: 'string', enum: ['jpeg','png'],
             description: 'jpeg（默认，小且快）适合正文/扫描页；png 适合细线条、公式、表格' },
}
```

**`region` 与 `rect` 的关系（v3.1 新增，几何上是同一个东西）**：

| 事实 | 说明 |
|---|---|
| 几何唯一的原生表达是 `RegionRect = [x0,y0,x1,y1]`（0–1） | `REGION_PRESETS` 只是 5 个预置矩形：`full=[0,0,1,1]`、四象限各 `0.5×0.5`（`render-geometry.ts:21-28`） |
| 二者**互斥**，同时给 ⇒ `execute` 抛错（不静默取一个） | 静默择一会让"我以为裁了 A 其实裁了 B"变成不可察觉的错误（§18-2 同源纪律） |
| 越界/退化（`x0≥x1`、超出 `[0,1]`、非 4 元数字）⇒ **抛错并给出合法范围** | 参数错属"模型可纠正重试"类（§0.5-4），不占浏览器、不花 token |
| `rect` 的缓存键 = **归一化后的矩形**，不是原始入参 | `[0,0,0.5,0.5]` 与 `region:'top-left'` 命中同一条缓存（语义相同就该复用，否则同图渲染两次） |
| 为什么不扩成 16 块枚举 | 主理人实测：4×4 网格把正文裁到 735×387，模型读成碎片（`ferent langua they often pro faces`）—— 空间太小反而丢上下文。粒度交给模型按内容自选，比我们猜网格强 |

返回值见 §9.2。**渲染参数公式**（唯一实现，写进 `render-geometry.planRender`，禁止另写）：

```ts
const r = regionRect(region ?? rect ?? 'full')      // 归一化矩形：预设查表 / 分数矩形校验后换算
const wPt = vp1.width * r.w, hPt = vp1.height * r.h // vp1 = page.getViewport({scale:1})（pt，已应用 /Rotate）
const scale = Math.min(
  maxEdge / Math.max(wPt, hPt),                     // 长边约束（作用于【输出图】）
  Math.sqrt(maxPixels / (wPt * hPt)),               // 面积约束（防方页/超宽页超预算）
)
width  = floor(vp1.width  * scale * r.w)
height = floor(vp1.height * scale * r.h)
// 渲染时用 render({ viewport: getViewport({scale}), transform: [1,0,0,1, -floor(vp.width*r.x), -floor(vp.height*r.y)] })
```

**注意 `rect` 让"分辨率杠杆"更容易被误用**：裁剪尺度是 `scale ∝ 1/max(w·r.w, h·r.h)`，所以 `rect` 越小 ⇒ 输出图长边仍顶到 `maxEdge` ⇒ 每格源像素继续下降（更清晰），但**上下文也越少**。所以 `rect` 不是"越大越好/越小越好"，而是"刚好套住要看的东西"。探针与 `guidance` 都不鼓励把 `rect` 缩到正文一行以下——那正是实测读成碎片的那档。

`maxEdge` 默认 **1500**、`maxPixels` 默认 **1_650_000**（≈1024 token 的承载面积）。夹取 `maxEdge ∈ [600, 2048]`：低于 600 会被 provider **上采样**（纯浪费 token 与字节），高于 2048 触附件归一化降采样。

**编码**：`canvas.toDataURL('image/jpeg', 0.85)` / `'image/png'` → `Buffer.from(b64,'base64')` → `ctx.attachments.saveImage({ data, mediaType, name })`。**不自写编码器**。

**与 dsh 硬约束的衔接**：`output.render` 返回 `[{type:'text'},{type:'image',attachment}]`（§0.1）；日志只存引用，字节进 attachment store（`packages/attachment/attachment/src/index.ts:186`；引用结构 `types.ts:11-32`）。

### 0.5 Q4 渲染链路的设计面（v3 全部换新）

#### (1) PDF 字节怎么给页面：**裁决 = `context.route` 拦截，不占端口**

两种可行方式，我实测后选 route：

| 方式 | 实测 | 结论 |
|---|---|---|
| 进程内临时 HTTP 服务（随机端口、bind 127.0.0.1） | 可行（v2 实测 4.4/1.17 均成功） | 否：占端口、需路径穿越防护、需一次性 token、需 `server.close()` 生命周期 |
| **`context.route('**/*')` + 假 origin 直接 `fulfill` 字节** | **可行**：boot 87–101 ms，render 85–150 ms，尺寸/字节与 HTTP 方案**完全一致**（1.17 p1 → 1126×1500 / 329 KB jpeg；4.4 p1 → 1137×1500 / 267 KB）；route 命中 4 次（HTML/`pdf.min.mjs`/`pdf.worker.min.mjs`/PDF）；**外网请求实测被 abort**（页面内 `fetch('http://example.com/x')` → `BLOCKED Failed to fetch`） | **是** |

假 origin 用保留域名 `http://lit-page.invalid`（`.invalid` 由 RFC 2606 保留，永不解析；即使 route 漏配也不会真发出去）。HTML 由 route 内联返回，模块路径同源。

#### (2) 浏览器生命周期

| 决策 | 结论 | 理由 |
|---|---|---|
| 启停策略 | **进程内复用**：`browser` 懒启动一次 + `context` 一次 + `page` 复用 | 实测 launch 266 ms，而热渲染 24–33 ms ⇒ 每次调用启停会把 90% 时间花在启动上 |
| 冷启动账 | 首调 ≈ 266（launch）+ 87–101（boot）+ 85–150（首渲染）≈ **0.45–0.5 s** | 探针实测；`timeoutMs` 留 25 s 余量 |
| doc 缓存 | 页面内 `window.__docs: Map<key, {task, doc}>`，key = `path|mtimeMs|size`，LRU 2，淘汰时 `task.destroy()` | **API 纠错**：`doc.cleanup()` 存在、`doc.destroy()` 不存在；`loadingTask.destroy()` 才释放 worker |
| 内存 | 单页 canvas ≤1500×1500×4B ≈ 9 MB；doc LRU 2；Chromium 常驻内存未精确测量（§15-4） | — |
| 空闲回收 | `idleTimeoutMs`（默认 300 s）：无调用则 `browser.close()`，下次调用重新 launch | 内存 vs 体感的取舍；可由 profile 设 0 关闭 |
| 崩溃恢复 | `page.on('crash')` → 标记 page 失效 → 下次调用 `newPage()` + 清 doc 缓存；`browser.on('disconnected')` → 标记失效 → 下次 `chromium.launch()` | 崩溃只影响这一次调用（隔离的意义） |
| 并发 | `isConcurrencySafe: () => false`；单 page 串行渲染（内部再加一个 promise 队列，防两个工具调用同时进同一 page） | 单 browser/page 是共享可变状态 |
| 启动参数 | **不加 `--no-sandbox`**（Windows 非容器，默认沙箱可用）；**不加 `--single-process`**（它会把页面崩溃升级成整个浏览器崩溃，正好抵消隔离收益）；不加 `--disable-web-security`（用假 origin 同源即可） | 安全默认 + 保留隔离 |

#### (3) pdf.js 资源路径：一个配置键 + 成对断言 + **资源面清点**（v3.1 订正）

`pdfjsAssetDir` **两种写法都接受**（启动期归一化，不是二选一）：

| 写法 | 该目录下有什么 | 归一化结果 |
|---|---|---|
| **包根**（推荐） | `build/`、`standard_fonts/`、`cmaps/`、`iccs/`、`wasm/` | 入口 js 在「包根/build/」，资源在各同名目录 |
| 指向 `build` 子目录 | `pdf.min.mjs`、`pdf.worker.min.mjs` | 回退到**上一级**取资源；上一级没有 `standard_fonts/`、`cmaps/` ⇒ **启动期抛错** |
| 省略 | — | 自动解析宿主 `pdfjs-dist` 包根（实测可达，6.3.289） |

**三条启动期断言（顺序即优先级）**：
1. `pdf.min.mjs` 与 `pdf.worker.min.mjs` **同目录成对**存在（同目录成对 ⇒ 结构上排除 API/worker 版本错配，§0.2 F2）。
2. `standard_fonts/` 与 `cmaps/` **非空**。缺任一个 ⇒ 抛错并给出两条修法（装依赖 / 指到包根）。
3. 打印一行资源面清点，缺项追加"降级：…"：`assets: standard_fonts=14 cmaps=168 iccs=1 wasm=7 build=6`。

**为什么第 2 条必须有（部署时必踩的坑，已写进错误消息）**：`pdfjs-dist` 的 `build/` 目录里**也有** `standard_fonts/`、`cmaps/`、`iccs/`、`wasm/` 这四个同名子目录，但它们是**空的**。只校验两个 js 文件时，一个"只放了两个 js 的目录"会通过断言，然后每个字体/cMap 请求都被 route 回 404，pdf.js **静默退化成替代字形**：图照样出、看着正常、字形悄悄变糊。`iccs/`、`wasm/` 允许缺（只影响色彩管理与 JPEG2000/JBIG2 解码，走 JS 回退），但会被记账并打印"降级"，避免无声降质。

`assets:` 这一行同时被三处复用：启动日志、`verify-config.mjs`、`dev/inspect.ts` 探针——所以它是**部署验收的可观测点**，不是调试噪音。

#### (4) 超时与失败语义（映射到 error，不映射到 status）

| 故障 | 抛出的错误（`isError: true`） | 处置动作 |
|---|---|---|
| 渲染超时 | `Error('lit_page_image: render timed out after <renderTimeoutMs>ms (page <n>). The PDF may be oversized or the renderer wedged.')` | `page.close()`；browser 保留 |
| page 崩溃 | `Error('lit_page_image: the renderer page crashed while rendering page <n>')` | 标记 page 失效，下次重建 |
| 浏览器不可用 | `Error('lit_page_image: cannot start the headless browser: ' + causeMessage + ' — run `npx playwright install chromium`; on restricted hosts also check that TEMP/TMP is writable.')` | 下次调用重试 launch |
| pdf.js 资源缺失 / 资源面为空 | `Error('lit_page_image: pdf.js assets not found …; expected pdf.min.mjs and pdf.worker.min.mjs')`；资源面为空时另抛一条，消息含 `standard_fonts/`、`cmaps/` 与"`build/` 里的同名目录是空的" | 启动期就报（不等到调用） |
| 页码越界 | `Error('lit_page_image: pageNo <n> is out of range (1..<pageCount>)')` | 模型可纠正重试 1 次 |
| 取消 | `signal.reason` 原样抛出 | `page.close()` |

**绝不**把上述任何一条写成 `status: 'no_pdf'` 或返回空白图（§18-2）。

#### (5) 安全：外网零出口

- 唯一网络入口是 `context.route('**/*')`：非假 origin 的请求**一律 `route.abort()`**。实测页面内 `fetch('http://example.com/x')` → `Failed to fetch`，且 route 记录到 1 次被拦请求（探针已断言）。
- `/vendor` 路径只回 `basename` 在白名单内的文件（`pdf.min.mjs` / `pdf.worker.min.mjs`），杜绝路径穿越。
- 不加载任何远程 URL；PDF 字节从 `ctx.library.assetPath(no)` 读本地文件。
- 渲染一个用户本地 PDF **不会**产生外网请求；探针把这条做成回归断言（R-P3-5）。

## 4. 六层设计

### 4.1 E 执行循环

- **不新增循环**：一步工具调用。终止由 V 层（确定性断言）判，模型说"看到了"不算。
- **防跑飞三道保险**：① 上游轮次/token 预算；② `timeoutMs: 25000`；③ **次数闸** `maxCallsPerSession`（默认 20）——计数由 **`ctx.pageImageUsage` 提供**，它把"本会话渲染了几次"定义成**会话日志投影**（`key=litPageImageUsage`，`stateVersion:1`）：`tool/call` 每条都带工具名，数条数就是数调用次数 ⇒ 插件重载/进程重启后**从日志恢复，不清零**（v3.1 订正；进程内 Map 会白送一整份额度）。每图 306–1010 tokens，这是唯一按次线性增长的成本项。`maxCallsPerSession<=0` ⇒ 该工具**不注册**（连按钮都不给）。
- **失败分类与恢复**：见 §0.5-4 表（参数错/业务边界/环境协议/取消四类，环境协议一律 throw 且不自动重试）。
- **打转检测**：同 `(no,pageNo,规范化 rect,maxEdge,format)` 命中缓存 ⇒ 0 渲染；叠加 `maxCallsPerSession`；上游"连续同工具同参数"打断仍生效。计数与缓存是两件事——**命中缓存仍然算一次调用**（花的是模型看图那 ~1000 tokens，不是渲染 CPU），所以缓存不能用来绕闸。
- **墙钟预算与并行**：冷首调 ≈0.45–0.5 s，热渲染 24–150 ms。**不并行**（单 browser/page 串行 + 内部 promise 队列）。
- **流式与可中断**：工具步原子；`exec.signal` 贯穿"等浏览器/等渲染/写附件"。取消后副作用：最多一个已/未发布 attachment，业务库零副作用。

### 4.2 T 工具注册

- **注册**：`ctx.tools.register(defineTool({...}))`，`inject: ['tools','library','attachments','pageImageUsage']`；`pageImages`（渲染引擎）与 `llm` **不进 inject**，用 `ctx.get(...)` 在 `execute` 里取。为什么区别对待：`pageImageUsage` 是"没有它就不该有这个按钮"的护栏（缺 ⇒ 工具不注册）；`pageImages` 是"视觉通道可整块摘除"的能力，缺它要**调用时响亮报错**而不是让整个插件起不来（§17-8 同理，能力缺失 ≠ 装配错误）。
- **组合条件挂载**（照 `packages/fs/tool-fs/src/index.ts:88-94`）：无 `attachments`/`pageImageUsage` 不注册。
- **注册 ≠ 披露 ≠ 授权**：① 注册由 profile overlay 行决定（可 `disabled:true`）；② **披露**用 `ToolRegistrationOptions.when`（`contracts.ts:104-124`，可读 `context.modelSelection`）判定当前路由是否声明 image 输入；③ **授权**在 `execute` 内二次复核（镜像 `tool-fs/src/read-image.ts:120-132`：`llm.resolveModelInfo(provider, model)` → `inputModalities.includes('image')`）。
- **披露是"三态"，且"不能判定"一律披露**（v3.1，R1 表第 3 行）：这是与探针三态同源的一条纪律——**不要把"不知道"伪装成"不支持"**。
  | 判定结果 | 行为 | 理由 |
  |---|---|---|
  | 解析成功且含 `image` | 披露 | 正常路径 |
  | 解析成功且不含 `image` | **不披露** | 不给模型一个只会失败的按钮（省一轮试错与 ~2000 schema tokens） |
  | 解析不出路由 / 无 `llm` / `resolveModelInfo` 抛错 | **披露** | 静默把能力藏掉，用户永远不知道有这功能（§18-6）；披露后 `execute` 会以可读消息响亮失败 |
- **执行环境与影响半径**（v3 更新）：宿主进程 + Chromium 子进程；**无端口、无服务**；新增副作用限于：spawn 子进程、需要可写 `TEMP`、写 attachment store、**在会话日志里多出 `tool/call` 与投影 cell**（成本闸的计数来源，可审计）。不触及用户文件与业务库。
- **凭证**：不进执行环境（不读任何 key）；**外网零请求**（route 单闸门）。
- **披露序列稳定**：名称/描述/参数顺序全静态。**`rect` 的加入改变了 schema 字节**（v3.1）——这是一次性的前缀失效，只影响升级那一刻的历史会话缓存，不进"重写触发热点"清单。
- **描述要点**：可看任意页（含矢量页）；`region` 看小字且不加 token；`rect` 给更细粒度的自定义区域（与 `region` 互斥）；`maxEdge` 调小可省 token；`format` 取舍；"这是页面外观，不是 OCR——极小的字仍可能读错，读正文优先 `lit_read`"。

### 4.3 C 上下文管理

- **预算分配**（单轮）：系统指令+persona ≈620；工具 schema ≈2000；历史；**图片 306–1010/张（默认 1 张）**；本工具文本 ≈140。
- **外界内容消毒**：图像无可注入面；`guidance` 由我们生成（不含 PDF 文本、不含本机路径、无时间戳）。
- **前缀稳定**：`render` 是纯函数；`scale` 2 位小数、`coversPageFraction` 3 位小数；无浮点抖动。
- **重写与失效预算**：只追加，不压缩不重排；历史图片超预算时由上游 `compaction-image-offload` 处理，我们不介入。
- **结果复用**：§9.1 两级缓存（页面内 doc 缓存 + 进程侧渲染结果缓存）。

### 4.4 S 状态存储

- **不新建任何存储**。跨轮可见性由会话日志 + attachment store 承担（重启可由日志重建）。
- **唯一"自有状态"是成本计数，且它也不由我们持久化**（v3.1 订正）：`ctx.pageImageUsage` 把状态声明成 **`sessionProjections` 的一个 host-only 投影单元**（`key='litPageImageUsage'`，`stateVersion:1`），由框架折叠、由投影缓存（`session-projection-cache`）落盘。
  ```ts
  interface ImageUsageState {
    calls: number                // 本 session 已提交的 lit_page_image 调用条数（**含**正在执行的那次）
    inheritedEventCount: number  // fork 继承前缀长度：继承来的事件不计本 session 的账
    seen: string[]               // 最近 64 个 callId（幂等：同一事件折叠两次不重复计数）
  }
  // 折叠规则：event.seq < inheritedEventCount ⇒ 忽略；type!=='tool/call' ⇒ 忽略；name!=='lit_page_image' ⇒ 忽略
  ```
  | 语义 | 行为 | 为什么这样定 |
  |---|---|---|
  | 同一会话续轮 | 同 `Session` ⇒ 同 cell ⇒ **连续累计** | 预算是会话级的，不是"每轮 20 次" |
  | 插件重载 / 进程重启 | 新 registration 首次 `stateOf()` 时**从会话日志惰性折叠重建**（有 checkpoint 缓存加速）⇒ **计数恢复，不归零** | 这正是"进程内 Map"被判定为缺陷的地方——重载等于白送一整套额度 |
  | fork / 子 agent | 继承前缀**不计账**（`inheritedEventCount`），子 agent 是独立 session ⇒ 各自 20 次 | 行为可预期（否则"各自 20 次"取决于插件注册时机）；**这是已知后门，如实记录不假装堵住**——跨 session 全局配额要上游给归属，本插件不越界 |
  | 并发同 batch 两次调用 | 可能读到同一计数（±并发度抖动），但**不会绕过闸门**：超过 `max` 之后每次读到的都 `> max` | 边界附近允许 ≤并发度的抖动，比"为了精确而加锁串行派发"便宜得多 |
  | 缺 `sessionProjections` | **插件起不来**（`static inject` 硬依赖），不退化成进程内计数 | 退化恰好制造"静默清零"。宁可不给按钮 |
  | `maxCallsPerSession<=0` | 工具**不注册** | 比 `when` 恒 false 更干净：不占 schema 体积 |
- **计数方向（后人不要"顺手修正"）**：`tool/call` 由执行器在 `execute` **之前**写入（`packages/core/tools/src/batch.ts:243-249` 的 `BatchSettlement.start()`），所以 body 里读到的 `calls` **已含本次** ⇒ 边界判定是 `used > max`。写成 `>=` 等于每次会话白送一次、实际只给 `max-1` 次。
- 并发写：内容寻址 + 原子发布，幂等。
- 幂等键：图像字节 sha256；无业务库写入 ⇒ 无"超时但已生效"二义性。
- **证据版本绑定**：`(pdfPath, mtimeMs, size, pageNo, 归一化 rect, maxEdge, format, RENDERER_VERSION, PDFJS_VERSION, ENCODER_VERSION)`；PDF 重下或渲染器升级都改变证据身份（§15-3）。`rect` 用**归一化后**的四元组入键，使 `[0,0,.5,.5]` 与 `'top-left'` 共享缓存。

### 4.5 L 生命周期钩子

- 不新增 hook；如需收紧用既有 `tools/pre-execute` guard。
- **人在回路四档**：本特性 = **自动执行 + 执行后可见**（只读 + 只增上下文；影响半径 = 多了 ≤1010 tokens，新会话可撤销）。**不进"执行前确认"**。若将来加"回写批注"，必须升档。
- **纵深**：T 层三层分离 + `execute` 二次能力复核 + route 单闸门（安全纵深）。
- **卸载清理**：`ctx.effect(() => () => { void dispose() })`，`dispose()` = `browser.close()` + 清缓存；空闲回收（§0.5-2）+ 崩溃重建都收敛在这一个文件里。

### 4.6 V 评估接口

- **谁验证**：确定性探针 + 单测，不用模型自评。
- **可量化断言**：见 §1 成功标准与 §16 表。
- **生成者/评估者分离**：读图模型是生成者；验收是脚本（独立上下文、不看推理）。
- **工具回执 ≠ 业务事实**：回执只证明"图已渲染并入消息"，不证明模型看懂了；后者靠 L4 抽样 + §7 已有的一次人工对照（标题正确）。

## 5. 模型组合与任务分派

- **形态判定：A（单智能体 + 单模型）**。显式质疑：
  - 给"看哪页/哪个象限"配便宜决策模型？**否**——答案集不封闭，错判代价不对称（多一次往返 + 306–1010 tokens）。
  - 把读图拆子 Agent？**否**——读图结论要与 `lit_read` 互证，拆出去把整合成本翻倍，且要重开浏览器/重解析。
  - 用快模型判断"这页值不值得看"？**否**——代码层零成本。
  - ⇒ **形态 A 成立，分档不必要**。

| 步骤 | 档位 | 理由 | 成本/延迟预算 |
|---|---|---|---|
| 选页/选 region/选 maxEdge | 主 LLM | 取决于意图，开放集 | ~30–60 tokens |
| 渲染参数（scale/canvas/裁剪） | 确定性代码 | 公式可断言 | 0 token / <1 ms |
| 栅格化 + 编码 | Chromium（确定性） | 同输入同输出（同版本） | 0 token / 24–150 ms |
| 读图叙述、与正文互证、引用 | 多模态 LLM | 唯一 image 模态档 | 306–1010 vision tokens + 输出 |
| 验收 | 确定性脚本 | 客观 | 0 token |

- **预算分配**：文本 ~5–7k；图片按档 306（`maxEdge=800`）/1010（默认 1500）；闸 20 次/会话 ⇒ 单会话图像预算上限约 20×1010 ≈ 20k tokens（**这条要写进成本监控口径**）。
- **缓存与重算账**：历史前缀只追加；**重写触发点：无**。缓存命中 ≠ 消息不增长（同页重看仍 append）。
- **级联升级**：路由不支持 image ⇒ 不披露；读图质量不足 ⇒ 人工切 `deepseek-v4-pro`；不做自动升级。
- **降级链**：`deepseek-flash` 不可用 → 其它声明 image 的模型 → 都无 ⇒ 不披露 ⇒ 纯文本路径。**降级只改 profile。**
- **评估者档位**：无模型裁判环节（验证强度阶梯最高级）。

## 8. 关键接口签名

### 8.1 数据源接口

**(A) `ctx.library`：不新增方法**。`assetPath(no): string | null`（`service/library.ts:41`）已足够；把渲染塞进 library 会让每个 Provider 都被迫带一个浏览器（反面选项见 §20）。

```ts
export interface RenderRequest {

  pageNo: number                  // 从 1 开始
  region?: RegionSpec             // 预设名 或 [x0,y0,x1,y1] 分数矩形；默认 full
  maxEdge?: number                // 默认 1500，内部 clampMaxEdge 夹到 [600,2048]

  mediaType: 'image/jpeg' | 'image/png'

  height: number
  scale: number
  rect: [number, number, number, number]   // 归一化裁剪矩形（回显，便于复现与入缓存键）
```

**契约注记（v3.1，诚实标注唯一泄漏）**：`pdfPath: string` 把"输入是**本地 PDF 文件**"写进了契约。将来接远程 URL 或字节流来源，要把入参收成 `source: { path } | { bytes, mediaType } | { url }`——**工具层改一行**（它现在只把 `assetPath()` 的返回值原样传进来），`page-image-source.ts` 里"读 PDF 字节"那两处（`statPdf` 与 route 的 `/doc.pdf`）跟着换即可。其余入参与出参都与实现无关，所以**换 Provider（Chromium 渲染 → 内嵌位图 → 远程渲染服务）不改工具层**——这就是这个 seam 值得存在的检验口径。

`render` 内部流程（固定顺序）：

```
1. 启动期断言已在 constructor 完成；此处只做懒启动
2. 若 browser 未就绪或已 disconnected：browser = await chromium.launch(); context = await browser.newContext()
   → context.route('**/*', handler)  // 只在 context 创建时注册一次
3. 若 page 未就绪或已 crash：page = await context.newPage(); await page.goto(ORIGIN + '/')
   await page.waitForFunction(() => window.__litPageImageReady === true)
4. page.evaluate(renderInPage, { pdfPath, pageNo, region, maxEdge, maxPixels, mime, quality })
     页面内：按 path|mtime 查 window.__docs；未命中则 getDocument({ url: '/doc.pdf?doc=<docKey>' })
             → planRender(...) → canvas → render(viewport@scale, transform) → toDataURL
5. base64 → Uint8Array（Node 侧解）
6. 打点：renderedAt、scale、rect、bytes（供探针与日志）
// 任何 throw 都走 §0.5-4 的错误映射；finally 不关 browser（复用）
```

`route` handler（唯一网络闸门，**顺序写死在这一个函数里**；v3.1 措辞订正见 §17-8）：

```
const ORIGIN = 'http://lit-page.invalid'          // RFC 2606 保留域名，永不解析
for each request:
  if (url.startsWith('data:') || url.startsWith('blob:')) return route.continue()  // 进程内资源，不可能出网
  if (!url.startsWith(ORIGIN)) { 记账 blocked[]; return route.abort() }            // ← 这一行就是"外网零出口"

```

```
ok:
第 <pageNo>/<pageCount> 页已渲染（region=<region>，<width>x<height> px，覆盖页面 <pct>%）。
这是页面外观，不是 OCR：极小的字仍可能读错；正文引用优先用 lit_read。
```

### 8.4 `ctx.pageImageUsage`：成本闸 seam（v3.1 新增）

```ts
// service/page-image-usage.ts
import { Service, type Context } from '@deepseek-ai/cordis'
import { z as zod } from 'zod'
import type { Session } from '@deepseek-ai/dsh-session'
import type { ProjectionDefinition, ProjectionHandle } from '@deepseek-ai/dsh-session-projection'

export const name = 'lit-page-image-usage'
export const COUNTED_TOOL = 'lit_page_image'      // 投影内硬编码：统计的是"这个工具的调用条数"
const SEEN_CAPACITY = 64                          // 状态必须是有界 JSON（持久化缓存的前提）

export interface ImageUsageState {
  calls: number                // 本 session 已提交的 lit_page_image 调用条数（含正在执行的那次）
  inheritedEventCount: number  // fork 继承前缀长度：继承来的事件不计本 session 的账
  seen: string[]               // 最近 64 个 callId（幂等保护）
}

export const litPageImageUsage: ProjectionDefinition<'litPageImageUsage', ImageUsageState> = {
  key: 'litPageImageUsage',
  stateVersion: 1,             // 字段或折叠语义变化必须 +1，否则旧持久化行会被前向折叠成垃圾
  stateSchema: zod.object({
    calls: zod.number().int().nonnegative(),
    inheritedEventCount: zod.number().int().nonnegative(),
    seen: zod.array(zod.string()),
  }),
  init: (_header, inheritedEventCount) => ({ calls: 0, inheritedEventCount, seen: [] }),
  apply: (state, event) => {
    if (event.seq < state.inheritedEventCount) return state          // fork 前缀不算账
    if (event.type !== 'tool/call') return state
    if (event.data.name !== COUNTED_TOOL) return state
    const callId = String(event.data.callId)
    if (state.seen.includes(callId)) return state                     // 幂等
    return { calls: state.calls + 1, inheritedEventCount: state.inheritedEventCount,
             seen: [...state.seen, callId].slice(-SEEN_CAPACITY) }
  },
  // 纯 host 侧单元：不声明 wire ⇒ 不进客户端快照（不污染 wire 协议）
}

export class PageImageUsage extends Service {
  static inject = ['sessionProjections']        // 硬依赖：注册不出投影 ⇒ 插件起不来
  private handle!: ProjectionHandle<ImageUsageState>
  constructor(ctx: Context) { super(ctx, 'pageImageUsage') }
  protected async [Service.init](): Promise<void> {
    this.handle = await this.ctx.sessionProjections.register(litPageImageUsage)   // 必须 await 后再对外可用
  }
  used(session: Session): number { return this.handle.stateOf(session).calls }
}
```

三条被源码锁定的性质（改动前请先读这几行）：

| # | 性质 | 依据 |
|---|---|---|
| 1 | `calls` **含**正在执行的这一次 | `tool/call` 在 `execute` 之前入日志（`core/tools/src/batch.ts:243-249`） |
| 2 | 重载后从**日志**重建，不归零 | `sessionProjections.register()` 的 cell 首次读取时对既有事件惰性折叠（`init`+`apply`），并有 checkpoint 缓存加速 |
| 3 | 不能用 `session.eventAt/snapshotEvents/ownEvents` 读日志 | 三者均已 `@deprecated` 且注明 "new calls are prohibited"（`core/session/src/index.ts:714/728/745`）；投影是官方"读历史事件"的通道 |

```ts
/** 页面内（浏览器侧）：document 缓存，key = `${path}|${mtimeMs}|${size}`，LRU 2 */

// 淘汰：await entry.task.destroy()    ← loadingTask 才有 destroy；doc 只有 cleanup()

/** 进程侧：渲染结果缓存，LRU 8（v3.1：region 改为归一化 rect + 区域面积，枚举与矩形因此共享缓存） */
interface RenderCacheKey {
  pdfPath: string; mtimeMs: number; size: number
  pageNo: number
  rect: readonly [number, number, number, number]   // 【归一化后】的四元组，不是原始入参
  maxEdge: number; maxPixels: number; format: 'jpeg' | 'png'; jpegQuality: number
  rendererVersion: string; pdfjsVersion: string; encoderVersion: number
}
interface RenderCacheEntry {
  bytes: Uint8Array; mediaType: 'image/jpeg' | 'image/png'
  width: number; height: number; scale: number
  rect: [number, number, number, number]
  page: { widthPt: number; heightPt: number; pageCount: number }
  cacheKey: string              // 由 PageImageRenderer 回给 Consumer，用于附件引用缓存
}
/** 进程侧：attachment 引用缓存，LRU 8（键 = RenderCacheKey 的 hash 串） */
type AttachmentCache = Map<string, ImageAttachmentRef>

/** 会话侧（唯一"有状态"的东西，且它由框架折叠、不由我们落盘） */

```

**为什么缓存键用归一化 `rect` 而不是原始入参**：`region:'top-left'` 与 `rect:[0,0,0.5,0.5]` 是同一个区域，语义相同就必须共享缓存；否则同一张图会被渲染两次、写两个 attachment、白花两份 token。这属于"结果复用"（经济性三视角之一）而不是微优化。

```ts
  image: { attachmentId: 'sha256:…', mediaType: 'image/jpeg', bytes: 329222,

           coversPageFraction: 1 | 0.25,               // 3 位小数
```

三项纪律：
1. `image.rect` **恒有值**（含 `region` 预设的情况）——它是"这次到底看了哪一块"的唯一可复现凭据；模型与审计都读它，而不是去反解 `region` 名字。
2. `region` 只作**标签**（枚举名或字面量 `'rect'`），**不参与**判定；`coversPageFraction` 由 `rect` 面积算出（3 位小数），三者互为校验。
3. 形状固定、字段序固定、无时间戳/无本机路径 ⇒ 前缀稳定（§4.3）。`null`/缺失字段一律不出现（可省字段整体省略），不用 `null` 占位。

`ImageAttachmentRef`（`packages/attachment/attachment/src/types.ts:11-32`，不可改）：`attachmentId`（`sha256:` + 64 hex）、`mediaType`、`bytes`、`width`、`height`、可选 `name`、可选 `originalDimensions`。

## 11. 层间交叉检查

| 关系 | 说明 |
|---|---|
| T ↔ C | `when` 披露对同一路由稳定 ⇒ schema 序列与前缀不变；换模型才触发重写（跨模型缓存不共享），已知代价 |
| T ↔ L | 三层分离（注册/披露/授权）+ route 单闸门（安全）+ 卸载钩子（清理） |
| E ↔ V | E 只管调用收敛（超时/闸门/缓存）；V 用脚本判字节/尺寸/时延/digest |
| C ↔ S | 上下文存引用、存储存字节；日志重建不依赖内存态（例外：offload 后只剩占位文本） |
| T ↔ L（隔离） | 渲染在子进程：不可信 PDF 最坏崩一页，宿主存活 |
| **T ↔ 成本（v3.1 更新）** | **token 随面积线性到顶**（306→1010），不是固定费。所以成本闸既要做在"次数"上（20 次/会话），也要给模型 `maxEdge` 让它在"看清"与"省钱"间自选；**次数来源于会话日志投影**（`ctx.pageImageUsage`），缺失即不许注册工具 |

## 13. 生产级必答项（逐项回答）

| # | 必答项 | 结论 |
|---|---|---|
| 1 | 执行环境：工具在哪跑、凭证是否进执行环境 | 宿主进程（插件）+ **Chromium 子进程**（渲染，默认沙箱开启）。**无端口、无本地服务**（route 交付字节）。**凭证不进执行环境**：不读 key。**外网零出口**：`context.route` 单闸门——`data:`/`blob:` 放行、**非假 origin 一律 `abort()`**、假 origin 内未知路径回 404（404 是"origin 内没有这个文件"，不是出网；写成"一律 abort"会让后来人把 404 当 bug 修掉，见 §17-8）。实测 `fetch('http://example.com')` → `Failed to fetch`。写半径 = attachment store（内容寻址）+ 会话日志（`tool/call` 与我们注册的投影单元）；`app.db` 只读 |
| 2 | 错误回喂：失败如何作为观察回到上下文、如何分类恢复 | 四类：参数错 throw（可纠正重试 1 次）/ 业务边界 return `status` + `guidance`（换工具）/ 环境协议错 throw（§0.5-4 表，不自动重试）/ abort 传播。**禁止**把渲染失败写成 `no_pdf` 或空图。**披露判定同样是三态**：能判定"不支持 image"⇒ 不披露；判定不出来 ⇒ **披露**（让 `execute` 响亮报错），不静默藏能力 |
| 3 | 打转检测与熔断 | 同参命中缓存 + **`maxCallsPerSession=20`（计数来自 `ctx.pageImageUsage`，本会话日志投影，重载不清零）** + 上游同参打断。熔断：`renderTimeoutMs`（单页）/`timeoutMs:25000`（整体）/`maxEdge`+`maxPixels`（画布构造性封顶）/`idleTimeoutMs`（回收内存）/`maxCallsPerSession<=0`（不注册）。**命中缓存仍然计一次调用**——省的是渲染 CPU，不是模型看图那 ~1000 tokens |
| 4 | 记忆治理：可信度、归属、失效条件 | 不写长期记忆；图像属"本轮观察"，归属当前 session，**不得**升格为文献事实（persona 增补，§19）。失效 = PDF mtime/size 或渲染器/pdf.js 版本变化 |
| 5 | 外部副作用幂等 | 唯一持久副作用 = attachment 写入；幂等键 = 字节 sha256；原子发布；按 id 可读回同字节。浏览器/缓存非持久副作用，`dispose()` + `idleTimeoutMs` 兜底。不写业务库 ⇒ 无二义性 |

| 7 | 生成者与评估者分离 | 生成者 = 多模态主模型；评估者 = 探针/单测（独立上下文、不看推理、标准显式）。禁止"模型说看清了"作为验收 |
| 8 | 前缀稳定与缓存命中 | 稳定区：系统提示、工具 schema（静态、固定序）、历史；尾部：本轮 tool result。序列化确定：`render` 纯函数、`scale` 2 位、`coversPageFraction` 3 位、`rect` 4 位小数、无时间戳/路径/随机 id。**重写触发点：无**（v3.1 加 `rect` 参数是一次性 schema 变更，不构成持续性重写）。命中率口径：`token-meter` 命中/重算比 + 本插件缓存命中计数 |
| 9 | **验证口径本身是否可信**（v3.1） | 断言只允许 `passed` / `failed` / **`skipped`** 三态；`skipped` 必须打印"未判定"并进 `unverified[]`，**不得**计入通过数（详见 §16.0）。理由与 §18-2 同源：把"没法测"折叠成"过"，等于让验证器替系统撒谎。`gate.sh` 在 `skipped>0` 时必须把那几行列出来 |

## 15. 遗留问题与未知区（诚实标注）

1. **扫描件文字可读性：已由 §7 实测推翻我的悲观假设 —— 但仍有一条"最小字号"边界未量化。**
   §7：`1.17` p1 在 `570×759 / 108 KB`（306 tokens）就能正确读出主标题 `Software Agents`；`1140×1518 / 335 KB`（1010 tokens）额外读出页眉 `INTELLIGENT AGENTS`。⇒ **P3 不必降级为"只看图表"**。
   **仍未知**：① 正文小字（10 pt 级）是否能逐行读 —— 只有 4×4 细分（每格 ~5.8 pt）才可能；② 本库其余 12 篇（矢量页）的正文可读性没有对照实验（§7 只测了扫描件）。
   **占位方案**：默认 1500 长边（≈§7 高档）；`region` 提供 2× 放大；不承诺"能读正文"；L4 抽样补测。
2. **chromium/playwright 是"宿主安装内的包"而非我们的依赖**：上游若移除 `experimental/inspector` 或裁剪 devDeps，`import 'playwright'` 会失败。缓解：启动期断言 + 单文件适配层 + 错误消息给 `npx playwright install chromium`。
3. **像素随版本漂移**：chromium/pdf.js 升级会改渲染结果（抗锯齿、字体回退）。证据指纹已含版本；未做跨版本像素 diff（也不需要）。
4. **Chromium 常驻内存未精确测量**。已知量：单页 canvas ≈9 MB、doc LRU 2；整浏览器进程量级未测。因此引入 `idleTimeoutMs=300 s` 作为默认折中；**建议探针加一条内存打点**（`process.memoryUsage()` 只能看宿主，浏览器进程需 `tasklist`/`Get-Process`，跨平台性一般）。
5. **内嵌位图直取**（v1 主路径 / v2 已删）：**技术上可用**（§0.2.1 实测：legacy 构建 + 同版本 worker ⇒ `argsArray` 正常、`objs` 回调可解、1579×2106 像素正确）。**为什么不实现**：① 只覆盖"页面由整图构成"的页；② 对扫描页没有实际增益（provider 42px/格的天花板相同）；③ 需要自写 PNG 编码器（Node 侧无编码器）；④ 解析在宿主进程内。
   **v3.1 更正（我曾把这条说过头）**：它**不能**作为与渲染并列的第二 Provider——`render` 契约要求"任意页都给图或 reject"，而纯矢量页根本没有位图可取；没位图时只能 throw，那在工具层是 error 而非新的 `status`（两值枚举不能加）。所以它只能是同一 Provider 内的一条**快路径**，且省下的只是 85–150 ms 渲染，`pxPerCell` 还不占优（1579×2106 被 `maxEdge` 夹到每格约 35 源像素 vs 整页渲染 41.7）。**结论：seam 留着的理由不是"将来接内嵌图"，而是"把浏览器前提关进一个可禁用的插件 + 换引擎不动 Consumer"**。
6. **多页/批量**：不做（§17-6）。若实测"看 3 页"往返成本明显，可加 `pages: number[]`（≤3）——代价是要定义"部分失败"合并语义。
7. **`when` 披露门控时序未实测**：`ToolActivationContext.modelSelection` 是 step 捕获值，会话中途换模型会改变披露集合（⇒ 前缀变）。判断：可接受（换模型本就整体失效），需 L1 探针确认同一模型下不抖动。**v3.1 补充**：三态里"判不出来 ⇒ 披露"这一支会让**没有 `llm` 服务的测试环境**也披露工具（便于单测），代价是那种环境下模型能看到一个只会在 `execute` 报错的按钮——已知并接受（真机上 `llm` 恒在）。
8. **崩溃恢复未构造实测**：`page.on('crash')` / `browser.on('disconnected')` 是标准 API，但本机未刻意制造崩溃验证重建逻辑。占位方案：按 §0.5-2 实现，并在探针里加一条"kill 浏览器进程后调用一次应能重建"的用例（R-P3-14）。**测报告已补证一半**：`browser.on('disconnected')` 自愈实测通过（关句柄 → 自动 relaunch、像素一致）；`page.on('crash')` 仍只有读代码级证据，探针里标 `skipped`（§16.0）。
9. **`rect` 的"最优粒度"没有客观判据**（v3.1 新增）：裁剪越细 ⇒ 每格源像素越少（更清晰）但上下文越少，实测存在"细到读成碎片"的反向区间（4×4 网格、每个 735×387）。目前只有一条负面样本，**没有**"按内容自适应选 rect"的算法；也不打算做（那需要版面分析，属另一个能力）。所以 `rect` 暴露给模型自选，`renderText` 不提示它（§8.2）。

## 16. 风险点与验证方式（每条可被测试工程师独立复现）

### 16.0 验证口径：**三态**，验证器自身不许撒谎（v3.1 新增）

每一条断言只允许落在三种结果上，**没有第四种**：

| 结果 | 含义 | 记法 | 计入 `ok`？ |
|---|---|---|---|
| `passed` | 在本环境**实际判定为真** | `ok  <label>` | 是 |
| `failed` | 在本环境**实际判定为假** | `FAIL <label>` | 否（`ok:false`） |
| `skipped` | 本环境**无法判定**（缺前置：无浏览器/无权限/`tasklist` 看不见子进程/样本 PDF 缺失） | `skip <label> 未判定：原因文本` | 否，**也不算失败、更不算已验证** |

机器可读的 summary 必须是：

```json
{ "ok": false,
  "failures": ["<label>：<detail>"],
  "unverified": ["<label>：未判定：原因文本"],
  "assertions": { "passed": 37, "failed": 0, "skipped": 3 } }
```

**为什么这条要写进设计而不是留给测试习惯**：只有 pass/fail 两态的探针，会把"没法测"默默折叠成"过"——于是"37 条全过"里混着 3 条根本没跑。这跟 §18-2「故障不得伪装成业务为空」是**同一类错误**，只不过是发生在验证器身上而不是模型身上：**不知道 ≠ 没问题**。所以 `ok===null` 必须显式降级成 `skipped` 并进 `unverified[]`，人读的输出必须出现"未判定"三个字。

已知必须走 `skipped` 的三处（本机实测）：① 浏览器进程残留计数（沙箱里 `tasklist` 看不到 chromium 子进程）；② `page.on('crash')` 崩溃自愈（无干净注入手段，见 §15）；③ 样本 PDF 不在本机时的全部像素断言。

## 17. 本设计不做的事（范围红线，防蔓延）

1. **不改 03-code**（不新增路由、不改 `services/*`）：只读它的 PDF 文件；可选用它 vendor 的 pdf.js 静态文件。
2. **不改上游 `deepseek-harness-master/packages/**`**，不动安装拓扑，不给 `dsh-impl` 建 `package.json`。
3. **不新增任何 npm 安装、不引入原生模块**（Chromium 是 playwright 管理的浏览器二进制，不是 npm 原生插件；但必须在 README 承认它带来 ~150 MB 前置体积）。
4. **不自己写 PNG 编码器、不做 box filter**：canvas 负责缩放与编码。
5. **不做内嵌位图直取**（技术可行，见 §15-5；收益为负）。
6. **不做多页/批量**（一次一页）。
7. **不做 OCR / 文字层提取**（那是 `lit_read` 与 `needs_ocr` 的事）；本工具只给"页面外观"。
8. **不占端口、不起本地 HTTP 服务**（此条为红线，防回归到 v2 的临时服务方案）。字节交付**只允许** `context.route('**/*')` 这一条通道，且它的三段行为**逐条钉住**（v3.1 措辞订正，`service/page-image-source.ts:982-1000`）：
   | 请求 | 行为 | 是不是安全闸门 |
   |---|---|---|
   | `data:` / `blob:` | `route.continue()` 放行 | 否——进程内资源，不可能出网 |
   | **非假 origin** | **`route.abort()` + 记入 `blocked[]`** | **是。这一行就是"外网零出口"的全部实现** |
   | 假 origin 内路径不存在 | `route.fulfill({ status: 404 })` | 否——origin 之内不存在"出网"这回事；**保留 404 是有意裁决**：让 pdf.js 缺资源时的报错可读（`UnknownErrorException` 会指明哪个 URL 拿不到），改成 `abort` 只会得到一句笼统的 `Failed to fetch` |
   > 所以红线**不是**"一律 abort"——写成那样会让后来人把 404 当 bug"修掉"，反而丢掉一类可诊断性。真正不许动的是一条：**除 `data:`/`blob:` 之外，凡是 target 不是 `http://lit-page.invalid` 的请求，必须 `abort`**。
9. **不做页内坐标 → 文本 bbox 映射**；不返回 PDF 内部结构（`view` 之外）。
10. **不用 `agent.inject()`**，不扩 `MessageSourceMap`。
11. **不做 Web 端图片展示定制**（`presentCall` 只给 `generic` 卡片）。
12. **不做逐像素回归基线**（跨 chromium 版本必漂移）。

## 18. 魔鬼代言人反例（假设上线后会怎么坏）

**反例 1｜"能看任意页"被读成"能读任意字"。**
§7 证明大字号可读，但用户与模型会顺推"那正文也能读"。10 pt 正文在一格 42 源像素下仍偏小，模型可能给出流畅但错误的转写。
反制：`guidance` 固定"不是 OCR，极小的字仍可能读错，引用优先 `lit_read`"；persona 增补"看不到就不要引用"（§19）；验收拆成"取到图"与"读出字"两条，不合并宣称（§15-1）。

**反例 2｜渲染超时/崩溃被写成"空页/无内容"。**
若异常被吞成 `status:'no_pdf'` 或返回白图，模型会向用户宣称"这页没有内容"，而事实是管道坏了 —— **用错误信息污染业务事实**，且从模型输出完全看不出来。
反制：`status` 只有 `ok | no_pdf` 两值，`no_pdf` 只允许由 `assetPath()===null` 产生（代码结构锁死）；§0.5-4 的六种故障各自 throw（R-P3-6 专守）。

**反例 3｜`region` 被实现成"裁剪"而不是"放大"。**
若 `maxEdge` 被理解成"页面长边"，取象限只会得到 570×760 的一小块 —— token 从 1010 掉到 287，看着"省了"，分辨率却一点没升，模型反而更看不清。这是本设计最容易被写错的一处。
反制：`planRender` 唯一实现且被 R-P3-7 三条定量断言锁死；工具描述明写"同样 token 成本、分辨率约提高 2 倍"。

**反例 4｜route 漏配 → 请求真发到外网（安全）。**
若 handler 只写了白名单、忘了 `abort()` 兜底，一个意外 URL（字体、locale、map 文件）就可能真发出去，把"本地渲染"变成"数据外泄"。
反制：假 origin 用 RFC 2606 保留域名 `.invalid`（**永不解析**，即使漏配也发不出去）；handler 第一行就是 `if (!url.startsWith(ORIGIN)) return route.abort()`；R-P3-5 断言外网拦截计数 ≥1。

**反例 5｜模型反复看图把上下文顶爆。**
每轮 +306–1010 tokens，多轮后触发 `compaction-image-offload`，旧图变占位文本；模型"记得看过"但当前请求里没有图 ⇒ 引用失据。
反制：`maxCallsPerSession=20`；`guidance` 引导"有目的地分块看"；描述写明"同页重复调用命中缓存、不额外花 token"。

**反例 6｜浏览器/内存成为隐形泄漏。**
异常路径没清理 page、`dispose()` 没被调用、空闲不回收 ⇒ 残留 chromium 进程占内存，跑一天后机器变慢且没人知道是 agent 干的。
反制：`finally` 必 close page；`ctx.effect` 卸载 + `idleTimeoutMs` 回收；R-P3-14 用进程表断言；探针在异常路径也走清理。

**反例 7｜"宿主依赖"在换机时集体失效。**
新机没装浏览器、或上游裁掉 inspector 包 ⇒ 整类图片能力静默消失；若实现把它降级成"无图"，用户永远不知道有这功能。
反制：启动期断言 + `npx playwright install chromium` 提示；README 把 playwright/chromium 与 `dbPath` 并列；禁止 try/catch 包住启动断言（实现注释写红线）。

## 20. 与既有 seam 三角色的对应关系

| 角色 | `ctx.library`（既有） | `ctx.pageImages`（新增） | `ctx.attachments`（既有，复用） |
|---|---|---|---|
| Definition | `LibraryService`（`service/library.ts:35-42`） | `PageImageSourceService`（§8.1-B）+ `declare module` 扩 `Context` | `AttachmentStore` |
| Provider | `LibraryProvider` | `PageImageSource`（`super(ctx,'pageImages')`，内部持有 browser/context/page） | `attachment-local` |
| Consumer | 4 个既有工具 + **`lit-page-image`（只用 `assetPath`）** | `lit-page-image`（唯一） | `lit-page-image` + 上游 `read_image` |

**为什么不把 `renderPage()` 挂在 `ctx.library`**：seam 的价值是"换 Provider 不动 Consumer"。把渲染塞进 library 等于宣布"任何数据源 Provider 都必须带浏览器"——未来的 HTTP Provider（候选 a）恰恰不需要。拆开后 `ctx.pageImages` 可从"Chromium 渲染"换成"内嵌位图直取"（§15-5）或"远程渲染服务"，`ctx.library` 一行不动。**反面代价**：多一个 seam、多一行 patch；若主理人认为"文献能力就该一个 seam"，把 `render` 原样搬进 `LibraryService` 即可，其余不变。

**第 4 个 seam：`ctx.pageImageUsage`（v3.1 新增）**

| 角色 | 内容 |
|---|---|
| Definition | `PageImageUsage`（`declare module '@deepseek-ai/cordis'` 扩 `Context`）+ 纯单元 `litPageImageUsage: ProjectionDefinition<'litPageImageUsage', ImageUsageState>` |
| Provider | `PageImageUsage extends Service`（`super(ctx,'pageImageUsage')`，`static inject=['sessionProjections']`，注册在 `Service.init` 里 `await`） |
| Consumer | `lit-page-image`（唯一，`used(session)` 一次） |

为什么它值得单独成 seam，而不是工具里的一个字段：

| 理由 | 说明 |
|---|---|
| 换实现不动 Consumer | "次数"可以从「会话日志投影」换成「宿主集中配额服务」「按用户计费的远端配额」；工具只调 `used(session)` |
| 把状态放到正确的层 | 工具因此**无状态**（可热重载、可多实例），计数只跟 `Session` 走——这正是"重载不清零"的结构性保证，而不是靠程序员记得序列化 |
| 可独立禁用 | 想换配额策略只需替换这一行 patch；想临时放开可以给一个"恒返回 0"的 Provider，工具一行不改 |
| **诚实标注代价** | 多一个 109 行文件 + 多一行 patch + 让 `lit_page_image` 多一个硬依赖（`sessionProjections` 不在的 profile 里，视觉通道整体不可用）。这个代价换来的是"预算不会在重连后静默清零"——主理人明确点名要的属性 |

## 拟入库条目

> 按 `references/knowledge-policy.md` 的防污染标准整理（通用机制、零产品名硬编码、含"何时不用"），待主理人经 wiki-creator 编译进团队底座。

### 条目 1｜Flat-Cost Vision Channel ⇒ Crop, Don't Downscale（**v3 修正标题与机制**：面积计价 + 硬封顶）

- **核心思想**：视觉通道的计费是"每格若干像素、总量封顶"时，成本与细节是**同一个旋钮**（面积↑ ⇒ token↑ 且细节↑，到顶后细节不再涨）。因此存在两种完全不同的优化：①**降尺寸**——真省钱，但细节按面积等比下降（适合"只确认版式"）；②**裁剪重铺**——不省钱也不花钱，但把同样的格数压到更小的区域上 ⇒ 细节按覆盖面积反比提高（适合"看小字"）。把二者混为一谈（以为"缩小=省 token 又不变差"或"裁剪=省钱"）都会做错参数面。推论：工具必须**同时**暴露"尺寸上限"与"区域选择"，且区域语义必须定义在**输出图**上，否则会被实现成"裁一小块、分辨率不变"。
- **可迁移层**：T（工具参数设计）、C（图像成本核算口径：按格数/面积，不按"张"）、V（能力契约用"每格源像素"给上界）
- **案例**：某通道 1 格 = 14px patch × 3，总量 ≤1024 tokens。实测：整页 570×759 = 306 tokens（能读大标题）、1126×1500 = 1010 tokens（能读标题+页眉）、同页 1/4 象限铺满 1500 = 1010 tokens 但每格源像素从 41.7 降到 20.9（2 倍精细）且字节降至 1/2。⇒ "缩到 570 宽省 2/3 token"为真，"裁剪省 token"为假（裁剪的价值是清晰度）。
- **何时不用**：按瓦片/尺寸线性计价、没有每图上限的通道上，"裁剪换清晰"仍成立但"封顶后不再增长"不成立，需重算；无文字场景裁剪无收益。
- **对照问题**：你的图像成本按张、按面积还是按瓦片？有没有每图上限？工具里"缩小"与"裁剪"是不是两个独立参数？区域的语义约束输入还是输出？

### 条目 2｜Capability Contract with Explicit Abstention（显式弃权的能力契约）

- **核心思想**：能力只覆盖部分输入空间时，"尽力而为"有害——模型无法区分"没有这种内容"与"我们的管道坏了"，于是把缺失当事实继续推理。正解：边界编码成**可枚举 status**，每支带可执行下一步；**环境/协议故障必须与"业务上无此能力"分离**（前者一律抛错），并用代码结构锁死（某 status 只能由一个条件产生）。能力扩大时，契约要同步补上**上界**（分辨率/精度），否则用户期望会跟着无限升高。
- **可迁移层**：T（返回契约）、E（错误分类）、V（禁止把异常算作业务结论）、C（渲染文本即能力说明书）
- **案例**：反例——"渲染超时"降级成"无内容"，模型会向用户宣称"这页没有内容"；此类错误从输出完全不可察觉。另一方向——能力从"部分输入"扩到"全部输入"后，必须显式写"分辨率上界"，否则"能渲染"会被读成"能读扫描件正文"。
- **何时不用**：能力全覆盖时 status 枚举只增噪音；调用方是代码时用错误码即可。
- **对照问题**：哪些分支是"能力不足"、哪些是"业务为空"？实现出 bug 时模型会不会读成业务事实？能力扩大后"上界"那句更新了吗？

### 条目 3｜Isolate Untrusted Parsing Out of the Agent Process

- **核心思想**：agent 宿主是长寿命、持有会话与凭据的进程；把"解析不可信输入"（PDF/图像/压缩包/网页）的库放进宿主，等于让畸形输入的最坏后果（OOM/崩溃/解析器漏洞）落在 agent 身上。若能借到天然隔离的执行环境（浏览器子进程、容器、独立 CLI），即使多一次冷启动与一次跨进程传输，也应按"隔离优先"选型——宿主崩溃丢的是整轮上下文，子进程崩溃只丢一次调用。**配套收益**：隔离环境里的 API/worker 往往"同源成对"，天然消除版本错配这一类部署事故（本项目实测到跨目录取 API/worker 造成的版本错配故障）。
- **可迁移层**：P（执行环境/拓扑选型）、T（工具在哪执行）、L（权限与故障边界）、E（失败分类：子进程崩溃 ≠ 业务失败）
- **案例**：同一批 PDF 既能用宿主进程内的纯 JS 解析库打开，也能用"浏览器子进程 + 页面内解析"。后者多一次 ~250 ms 冷启动、一个可写临时目录前提，但换来任意输入可处理 + 解析风险外移 + 版本天然配对，净收益为正。反例：把不受控大文件解析放进宿主，最坏是整进程 OOM，会话与未落盘上下文一起丢失。
- **何时不用**：解析库成熟且输入可信（自己生成的中间产物）；冷启动压在交互关键路径且不可摊销；目标环境不允许起子进程。
- **对照问题**：agent 进程里正在解析哪些"别人给的东西"？解析崩溃时丢的是"一次调用"还是"整轮上下文"？隔离的冷启动能否在会话内摊销？API 与 worker/编解码器的版本由谁保证一致？

### 条目 4｜Three-Valued Verification：验证器不许把"没法测"折叠成"过"（v3.1 新增）

- **核心思想**：自动化验证的断言只有两种结论时（pass / fail），每一条"本环境无法判定"的用例都会被**静默**塞进 pass——于是"37 条全过"里混着 3 条根本没跑，而报告看上去完美。正解是把断言定义成**三值**：`passed` / `failed` / `skipped`，其中 `skipped` 必须携带"为什么判不了"，单独汇总（`unverified[]`），**既不进通过数、也不进失败数**；人读输出必须出现"未判定"字样。这与"故障不得伪装成业务为空"是同一类错误的两个发生位置：一个在系统里，一个在验证器里。
- **可迁移层**：V（评估接口的取值域）、E（报告与门禁）、L（发布门禁读哪几个计数）
- **案例**：探针原先只有 pass/fail；在沙箱里"浏览器子进程残留计数"根本看不到子进程（`tasklist` 为空），该条被算作 pass。改为三值后它进入 `unverified[]`，人一眼看到"3 条未判定：本环境看不到浏览器进程"，不再误以为进程泄漏已被验证。
- **何时不用**：环境完全受控且所有前置必然满足（纯函数单测）；此时三值只是噪音，二值足够。
- **对照问题**：你的测试报告里，"跳过"的用例现在显示成什么？门禁只看 `failed==0`，还是也看 `skipped==0`？"无法判定"的原因有没有被打印出来，还是只留一个沉默的绿色？

### 条目 5｜Put the Quota in the Log, Not in the Component（配额从事件日志派生，不在组件里计数）（v3.1 新增）

- **核心思想**：给一个能力加"每会话 N 次"的闸门时，最容易写的是组件内的 `Map<sessionId, count>`。它在热重载、进程重启、多实例、故障切换后**全部归零**——等于每次重连白送一整份额度，而且没人会察觉（额度是"上限"，不是"账单"）。正解：**把"发生过几次"定义为"日志里这类事件有几条"**，计数由日志折叠派生（并可被框架的投影/checkpoint 缓存加速）。组件的状态随之退化为无状态 → 可重载、可并行、可审计；顺带得到两个免费性质：①"这个数字是哪来的"永远可回答（看日志）；② 审计与闸门用同一个口径。
- **可迁移层**：S（状态存储位置的选型）、T（工具是否有状态）、E（预算/熔断）、V（可审计性）
- **案例**：把"本会话渲染了几次"定义成"会话日志里该工具 `tool/call` 的条数"后，重载/重启都自动恢复；同时在实现里发现一个**方向性坑**：若该事件在动作**之前**写入，则读到的计数**已含本次**，边界判定必须是 `> max`，写成 `>=` 会每次白送一次。
- **何时不用**：日志不持久、或事件并非"一次动作一条"（批量/合并写入）时，折叠会失真；极高 QPS 下逐条折叠成本高于一个原子计数器，此时用外部计数器并接受"清零点"要显式定义。
- **对照问题**：你这个额度存在哪？热重载后它还在吗？这个数字能追到源头吗？"动作"与"计数事件"的写入顺序确定了吗——边界写的是 `>` 还是 `>=`？

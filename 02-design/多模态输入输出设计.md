## 4. 六层设计（决策 + 落地规格）

### 4.1 E 执行循环
- **决策**：上传是 **SSE 循环外**的一次性请求（两步式 A2），不进 `runToolLoop`；提问 SSE 循环沿用 `pipeline.js` 既有逻辑，仅在「组装用户消息」一步注入图片 content parts。终止条件仍由 V（done 事件）+ 轮数上限（`config.chat.maxToolRounds`）+ 墙钟（`timeoutMs 90s`）三重保险（`loop.js` 已有）。
- **落地**：新增 `POST /attachments` 独立 handler；`postMessageTools` 在 `pipeline.js:76` 处把 `userText` 升级为「文本 + 图片 parts」。错误分类回喂沿用 `loop.js:118-122`（工具失败回 model 文本）；上传错误走 `AppError`→`errorMiddleware` JSON。
- **墙钟/并行**：上传可小并发（浏览器并行 POST 数个文件），后端各请求独立、`saveFile` 幂等无锁冲突；模型侧图片增大拉长 TTFT，由 5MB/图上限 + 4/消息计数约束（§9）。
- **可中断**：SSE 提问的取消已在 `pipeline.js:110-125` 实现；上传请求短促，取消即丢弃，落盘是 post-parse 一次性 `writeFileSync`，无半截副作用。

### 4.2 T 工具注册
- **决策**：上传端点**不是工具**（不进 `registry`），是普通 REST 资源操作，沿用 `assets.js` 上传的「手写 multipart + `express.raw`」形态。工具披露序列不变（`pipeline.js:37-40` 固定序），故稳定前缀不受扰动（知识库 `deterministic-serialization`）。
- **落地**：复用 `extractMultipartFile`（`assets.js:57-87`），新函数 `extractMultipartFiles`（返回全部 `file` part 数组，支持一次多文件）。`saveFile` 见 §4.4。
- **执行环境/凭证**：上传在本地 Node 进程；模型调用凭证在 `secrets.providers`（内存，`config.js:147-148`），**不进上传执行环境**；上传端点不触外部网络（无 SSRF 面）。

### 4.3 C 上下文管理
- **决策（核心）**：用户上传图以 **content parts 嵌在用户消息本体**（可变尾部），工具产图以**独立 `role:user` 消息**在 loop 尾部注入（`loop.js:125-141`）。两者都落在**可变尾部**，**绝不进 system + tools 稳定前缀** → 与知识库 `prefix-stable-context` 一致：前缀按最长公共前缀复用，图片这种易变内容只在尾部追加/重建，不触发前缀失效。
- **序列化确定性**：data URI 用 `Buffer.from(bytes).toString('base64')`（确定性，无随机）；caption/说明不含时间戳/路径（沿用 `buildCaption` 思路）。同字节同输出 → 满足 `deterministic-serialization`。
- **预算分配**：图片 token 计入 prompt 预算；系统指令/历史/工具结果/图片分区靠既有 `config.chat.*`（historyTurns、maxTokens）。图片无独立窗口配额，靠 §9 计数+字节上限兜底。
- **外部内容消毒**：用户图是「待分析数据」而非指令；模型侧按视觉输入处理，无注入面（图片不进 system prompt 文本）。

### 4.4 S 状态存储
- **决策**：附件**内容寻址**（`file_<sha256>`/`img_<sha256>`），幂等、天然去重、跨会话可复用（知识库 `result-memoization`）。引用冗余存于 `messages.attachments`（每消息一份引用，可接受）。
- **落地**：
  - `attachments.js` 新增：
    - `attachmentIdOf(bytes, prefix='img')` —— 泛化前缀（`attachments.js:21-24` 改为可传 prefix）。
    - `saveFile({bytes, mediaType, sniff=true})` → `(attachmentId, mediaType, bytes, width, height, sha256)`：前缀 `file_<sha256>`；`sniff` 时用 `sniffMediaType(buf)`（PNG/JPEG/WebP/GIF magic→`image/*`，否则 `application/octet-stream` 或入参提供的类型）；幂等写对象；**额外写侧车 `<objPath>.meta.json` = `{mediaType, width, height, bytes}`**，供下载路由取正确 mediaType/文件名（修 §1.1 缺口）。
    - `readAttachmentMeta(attachmentId)` → 读侧车；无则 `null`（旧 `img_` 对象回退 magic 嗅探）。
    - `readImageSize(buf)` → 轻量解析 PNG/JPEG/WebP 头得 `{width,height}`（无新依赖；不支持的格式返回 `null`）。
  - `session.js:insertUserMessage(chat, content, attachments=[])` 扩展：INSERT 增加 `attachments` 列（`JSON.stringify`）。SQL 见 §7。

### 4.5 L 生命周期钩子
- **决策**：上传端点过既有 `securityMiddleware`（Host/Origin/Content-Type），并加进 `allowMultipartPaths`（`app.js:42`）。无新增审批/人在回路（本地单用户，上传即用户本人意图）。
- **落地**：复用 `express.json` 之后的 `express.raw`（仅对该路由），在 `chatRoutes()` 内对该 POST 单独挂 `express.raw({type:['multipart/form-data','image/*','application/pdf'], limit: maxBytes+8MB})`。限流复用全局 `rateLimit`（`app.js:45`，120/min）。

### 4.6 V 评估接口
- **决策**：本功能无独立模型评估步骤。「模型是否真看到图」由 **E2E 断言**验证（§10），非模型自评（满足 production-checklist V 层「生成者≠评估者」：验证方是测试脚本读模型最终回答文本，不看推理）。
- **落地**：`04-test/e2e-multimodal-upload.mjs`（见 §10a）断言回答含对图内容的引用。

## 5. 模型组合与任务分派

- **形态判定**：**形态 A（单智能体 + 单模型）**。显式质疑：是否需要单独视觉模型？→ 否，`deepseek-chat`（→deepseek-flash）本身多模态、支持 `image_url`；引入第二模型=无谓多模型复杂度，违背「单 Agent 优先」。故形态 A 成立。
- **任务-模型分派表**

| 步骤 | 档位 | 理由 | 成本/延迟预算 |
|---|---|---|---|
| 附件落盘（multipart 解析、内容寻址写盘、尺寸嗅探） | 确定性代码 | 答案可枚举、无理解，纯 IO/哈希 | 忽略（本地 μs~ms） |
| 图片→data URI 注入（读盘+base64+拼 content parts） | 确定性代码 | 固定变换，无歧义 | 忽略（本地） |
| 多模态理解（就图作答、描述版面） | 强力 LLM（deepseek-chat） | 开放视觉推理，唯一承担者 | 受 §9 上限：≤4 图/消息、≤5MB/图入模；输出 `maxTokens=1600`、墙钟 `timeoutMs=90s` |

- **token 预算按档位分配**：仅 1 个档位（强力 LLM）承担所有理解；确定性代码零 token。图片 token 计入其 prompt 预算；**评估/验证步骤（E2E）在预算外**（测试期，非线上）。
- **缓存与重算账**：用户/工具图均在可变尾部，不贡献稳定前缀复用，但也不引发前缀失效（system+tools 不动）。`prefix-stable-context` 收益保留在 system+tools 段。
- **级联升级/降级链**：deepseek 不可用时无第二模型兜底（与现有 chat 一致，走 `E_UPSTREAM`→前端报错）；非本设计新增面。
- **评估者档位**：无（见 §4.6）。

## 7. 接口设计（路由 + 请求体 + 响应体，精确到字段）

### 7.1 新增：上传附件 `POST /api/chats/:id/attachments`
- 中间件：`express.raw({type:['multipart/form-data','image/*','application/pdf'], limit: config.chat.attachments.maxBytes + 8*1024*1024})`；该路径加入 `app.js:42` 的 `allowMultipartPaths`（否则被 `security.js:58` 拒）。
- 请求：
  - `Content-Type: multipart/form-data; boundary=...`
  - 单 part：`name="file"`，`filename="xxx.png"`（一次一文件；前端对所选多文件循环 POST）。
  - 也接受裸 `image/*` / `application/pdf` 原始体（与 `assets.js:173` 同思路）。
- 处理顺序（handler 落 `server/routes/chat.js` 新函数 `uploadAttachment`）：
  1. `loadChat(id)` 校验会话存在（复用 `session.js:loadChat`）。
  2. 取 body buffer；空→`E_BAD_REQUEST`。
  3. `extractMultipartFile(body, ct)`（`assets.js:57`）取 `file` part；裸体直接用 body。
  4. `bytes = buf.length`；`> config.chat.attachments.maxBytes` → `E_TOO_LARGE`，文案：`上传文件 ${bytes} 字节，超过单文件上限 ${maxBytes}（约 ${Math.round(maxBytes/1048576)}MB），请压缩后重试`（`maxBytes` 见 §9）。
  5. `mediaType = sniffMediaType(buf)`（图片→`image/png|jpeg|webp|gif`；否则入参/扩展名推断或 `application/octet-stream`）。本轮仅支持图片 + 常见文档；若 `!isSupported(mediaType)`（见 §9 白名单之外）→ `E_UNSUPPORTED`，文案：`不支持的文件类型：${mediaType}（本轮仅支持图片与 PDF/TXT/MD）`。
  6. 若为图片：`size = readImageSize(buf)`；若 `max(size.width,size.height) > config.chat.attachments.maxEdgePx` → `E_TOO_LARGE`，文案：`图片长边 ${edge}px 超过上限 ${maxEdgePx}px（本系统暂不支持自动压缩，请用更小的图）`。
  7. `ref = saveFile({bytes: buf, mediaType, sniff:false})`（写对象 + `.meta.json` 侧车）。
  8. 返回 201：`{ attachmentId, source:'user', kind, mediaType, width, height, bytes, url }`，其中 `kind = mediaType.startsWith('image/') ? 'image' : 'file'`；`url = /api/chats/${id}/attachments/${ref.attachmentId}`（`pipeline.js:43-45` 同款拼法）。
- 错误：统一 `AppError` → `errorMiddleware` 返回 `{error:{code,message}}`。

### 7.2 扩展：提问 `POST /api/chats/:id/messages`（既有，`pipeline.js:85`）
- 请求体新增可选字段：
  - `attachmentIds: string[]` —— 本次用户消息携带的附件 id（来自 7.1 的上传响应）。缺省 `[]`。
- 校验：`attachmentIds.length > config.chat.attachments.maxPerMessage` → `E_BAD_REQUEST`，文案：`本次附件 ${n} 个，超过每消息上限 ${maxPerMessage} 个`。
  对每个 id：`readAttachment(id)` 必须非 null，否则 `E_NOT_FOUND`（防止引用不存在/越权探测）。其 `source` 固定视为 `user`。
- `insertUserMessage` 改为带 `attachments`（§4.4 / §8 JSON 形状）。
- SSE 事件流**不变**（`meta/tool/tool_result/image/delta/citation/done/error`）。用户附件不靠新事件，靠前端乐观渲染 + 历史回看 `messages.attachments`（见 §8、§11 A3）。

### 7.3 扩展：回源 `GET /api/chats/:id/attachments/:attId`
- 既有（`chat.js:73-85`）。新增查询参数 `?dl=1`：
  - 有 `dl=1`：`res.setHeader('Content-Disposition', 'attachment; filename="<attId>.<ext>"')`，`<ext>` 由 `readAttachmentMeta` 的 mediaType 映射（png/jpeg/webp/gif/pdf/txt…）。
  - 无 `dl`：维持 `inline`（img 元素直接显示）。
  - `Content-Type` 优先取 `readAttachmentMeta` 存值，回退 magic 嗅探（修旧 `img_` 无侧车情形）。

## 11. 与既有引擎衔接（关键，避免冲突）

1. **用户图进入 `buildToolMessages`**：`pipeline.js:76` 由
   ```js
   messages.push({ role: 'user', content: userText });
   ```
   改为：
   ```js
   const userContent = buildUserContent({
     text: userText,
     imageAttachments: resolvedUserImages,   // 从 body.attachmentIds 解出
     read: readAttachment,
     maxBytes: cfg.attachments.maxInjectBytes,
     maxPerTurn: cfg.attachments.maxInjectPerTurn,
   });

   ```
   `buildUserContent`（新函数，置于 `image-inject.js` 或 `pipeline.js`）：无图→返回 `userText`（string，保持历史行为）；有图→返回 `[{type:'text',text},{type:'image_url',image_url:{url:'data:...;base64,...'}},...]`，超 `maxBytes` 的单图进 `skipped` 说明（与 `buildImageInjection` 同账本）。
2. **与 `buildImageInjection`（工具图）并存不冲突**：工具图在 `loop.js:125-141` 以**额外 `role:user` 消息**注入（循环内每轮尾部）；用户图在**首条 user 消息 content parts**（循环外组装）。两者通道正交、互不覆盖。同一轮可同时发生（用户传图 + 模型调 lit_page_image），模型先看到用户图（user 消息），再在工具结果后看到渲染页图（注入消息）。
3. **`attachments` 落库富集**：`pipeline.js:188-200` 的 `for (const a of info.attachments)` 改为 `attachments.push({ ...a, source:'tool', kind:'image', toolName: info.name, pageNo: info.args?.pageNo ?? null })`，使工具图也带 `source/kind`（前端 `appendImage` 只读安全子集，兼容）。
4. **用户附件落库**：`postMessageTools` 调 `insertUserMessage(chat, content, userAttachmentRefs)`（§8.1），`userAttachmentRefs` = `attachmentIds` 解出的完整形状（含 `source:'user'`）。
5. **SSE 是否新事件**：**不新增**（A3）。用户气泡由前端乐观渲染（携带 pending 引用），历史回看由 `listMessages` 的 `attachments` 字段驱动；`meta` 事件已带 `messageId=userMsgId`（`pipeline.js:152-159`），前端据此对应。

## 15. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| R1 data URI 使请求体变大（base64 +33%） | 传输/内存峰值；deepseek 按图像像素计 token，base64 膨胀**不增 token** | 5MB/图上限（§9）；本地回环网络，传输成本可忽略 |
| R2 模型服务端无法访问 127.0.0.1 回源 URL | 若用 URL 注入则图不可达 | A1 选 data URI（与 `buildImageInjection` 一致），规避 |
| R3 用户图 + 工具图叠加 → token/延迟峰值 | 单轮最多 4+4=8 图，prompt 可能数十万 token | §9 各自≤4；全局合并上限为遗留项（见未知区） |
| R4 非图片文档进模型 | deepseek-flash 不支持文档多模态，会失败/忽略 | A4：文档仅落盘+占位，不注入（本轮回填） |
| R5 大图尺寸嗅探不支持 GIF/AVIF | width/height=null（仅展示缺尺寸） | 不影响功能；前端 caption 容错 |
| R6 `allowMultipartPaths` 漏加 → 上传被拒 | 403/400 | §7.1 明确改 `app.js:42` |
| R7 legacy 引擎不支多模态 | 切 legacy 时用户图被忽略 | 已知边界；本轮仅 tools 引擎支持（未知区） |

## 16. 魔鬼代言人（≥3 反例，反驳设计选择）

1. **反例：「应该用回源 URL 而非 data URI，省传输」。** 反驳：deepseek 服务端**无法访问** 127.0.0.1:7317（私网/同源限制），URL 不可达会直接失败；且现有 `buildImageInjection`（`image-inject.js:83`）已用 data URI，保持一致降低风险。base64 +33% 仅影响本机回环传输，不增模型 token（图像按像素计费）。
2. **反例：「上传应单步合并进提问请求（multipart 同时带文本+文件），少一次往返」。** 反驳：单步会把 SSE 流式接口变成 multipart，与 `postMessageTools`（`pipeline.js:85` 的 JSON body + SSE）结构冲突；且难做逐文件错误/进度/重试。两步式（先传后引）更契合聊天作曲式 UX，也与 `assets.js:171` 上传返回 JSON 的风格一致。
3. **反例：「应该新增 `attachment` SSE 事件做上传确认，前端更清晰」。** 反驳：上传是独立 REST 请求，其 JSON 响应即确认；新增事件增加前端/运维认知负担、且 `meta` 已带 `messageId` 对齐气泡。无收益，故 A3 不新增。
4. **反例：「文档（PDF）也应塞进模型上下文，让它读」。** 反驳：deepseek-flash 本轮仅支持 `image_url`，不支持文档多模态；大文档撑爆窗口且 token 昂贵。留接口+占位（A4）待模型能力扩展，是更稳的边界。
5. **反例：「用户图也该像工具图那样注入成独立 role:user 消息，逻辑统一」。** 反驳：用户图属于**用户本轮提问的一部分**，放进 user 消息 content parts 才语义正确（与文本同一条 user turn）；工具图是**工具结果**，只能以注入 user 消息呈现（text-only 适配器限制）。二者语义不同，分开更清晰，且均落在可变尾部不扰前缀。

## 17. 遗留问题与未知区（诚实标注）

1. **legacy 引擎多模态**：本设计仅在 tools 引擎生效；切 `config.chat.engine='legacy'` 时用户图被忽略。是否要 legacy 也支持？→ 未知，建议本轮不支持。
2. **全局图片合并计数**：用户图（≤4/消息）与工具图（≤4/轮）各自独立计数，未做全局合并上限；极端情况 token 峰值见 R3。建议后续合并到同一计数器。
3. **图片降采样**：超 `maxEdgePx` 当前直接拒绝（不降采样），因无图像库（sharp/jimp）依赖；如需自动压缩需引入依赖，超出本轮。
4. **GIF/AVIF 尺寸**：`readImageSize` 仅解析 PNG/JPEG/WebP；其余 `width/height=null`，不影响功能。
5. **跨消息附件复用 UI**：内容寻址已天然去重，但前端每次上传都新建引用；未做「复用历史附件」入口（可选增强）。
6. **模型图像 token 成本**：未实测 deepseek 图像计费；§9 上限按经验设，需上线后按 `usage` 观测调参（production-checklist「成本核算」）。
7. **大文件流式上传**：`express.raw` 一次性读进内存（limit 18MB）；当前 10MB 上限安全，若未来提上限需改流式写盘。

> 按 `knowledge-policy.md` 防污染标准整理；架构师不直接写知识库，随设计回传。

**条目（建议归类 `patterns/`，多模态输入类，可并入或紧邻 `efficiency-and-caching.md` 的 `result-memoization`）：**

- **name**: `multimodal-input-injection`（多模态输入注入）
- **group**: `patterns/multimodal`
- **可迁移到**: T（上传/工具产出）/ C（上下文布局）/ E（循环外资源操作）
- **核心思想**: 用户上传多模态内容经**内容寻址附件存储**后，以 **data: URI 嵌入用户消息 content parts**（同一 turn 的可变尾部）；工具产图以**独立 `role:user` 消息**在循环尾部注入（受 text-only 适配器限制）。两者通道正交、均不进 system+tools 稳定前缀。
- **案例**: 03-code 文献阅读 chat harness（v3 `messages.attachments` 列，`lit_page_image` + 上传双通道）；与 `image-inject.js:buildImageInjection` 并存。
- **何时不用**: 模型不支持 `image_url`（如纯文本模型）时不可注入；多租户需对附件做按用户隔离（本设计单用户未做）。
- **对照问题**: 你的多模态输入落在上下文前缀还是尾部？工具产图与用户上传图是否共用同一条注入路径？凭证/大文件有无进执行环境？
- **来源**: 本设计（2026-09-30，03-code 多模态输入输出设计.md）；置信度 verified（基于既有 `buildImageInjection` 实证）。

## 22. 核心数据结构

```ts
type AttachmentRef = {
  attachmentId: string;        // 形如 img_ 后接 sha256，或 file_ 前缀
  source: 'user' | 'tool';
  kind: 'image' | 'file';
  mediaType: string;           // image/png | application/pdf | ...
  width: number | null;
  height: number | null;
  bytes: number;
  toolName: string | null;     // source==='tool' 时为工具名
  pageNo: number | null;       // 工具产图所在页
};

// 落盘侧车（saveFile 写入对象路径同级的 .meta.json）
type AttachmentMeta = { mediaType: string, width: number|null, height: number|null, bytes: number };
```
（`messages.attachments` 列类型：`TEXT`，JSON 数组 `AttachmentRef[]`，见 §8.1。）

## 24. 层间交叉检查

| 关系 | 说明 |
|---|---|
| T ↔ C | 上传是 REST 资源操作（非工具），不进 registry；用户图经 C 层 content parts 入可变尾部，工具图经 C 层注入独立 user 消息 |
| C ↔ E | 用户图在 user 消息尾部、工具图在 loop 尾部，均不扰 system+tools 稳定前缀（prefix-stable-context） |
| S ↔ E | 附件引用落 `messages.attachments`；`insertUserMessage` 扩展携带 attachments，跨轮可回看 |
| L ↔ T | 新上传路径加进 `app.js:42` 的 `allowMultipartPaths` 白名单，否则被 security 中间件拒 |
| V ↔ C | 「模型看到图」由 E2E 脚本读最终文本断言，独立于生成过程（生成≠评估） |
| S ↔ T | 内容寻址保证同字节幂等，上传无锁冲突，可安全重放 |

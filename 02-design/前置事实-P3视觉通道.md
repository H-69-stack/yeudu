# P3「视觉通道」前置事实（主理人汇编，非设计）

> 本文只陈述**实测事实**与**约束**，不含方案取舍。方案由架构师在 P1 增量设计中裁决。

## 1. 原设计的前提已不成立

`dsh-impl/docs/02-落地方案.md` §4.3 把路径写作「PDF 页栅格化 → `ctx.attachments` → 用户消息图片块」，
默认「栅格化能力可用」。实测该前提不成立：

| 候选渲染器 | 实测结果 |
|---|---|
| `@napi-rs/canvas`（pdfjs 官方可选依赖） | **不可用**：`03-code/.npmrc` 设 `omit=optional`（D19「零原生模块」约束），主包未安装，仅残留 `@napi-rs/canvas-win32-x64-msvc` 平台二进制 |
| `pdftoppm` / `mutool` / `gs` / `qpdf` | **全部缺失** |
| `convert` | 存在，但是 `C:\Windows\system32\convert`（FAT→NTFS 磁盘工具），**不是 ImageMagick** |
| Windows 原生 `Windows.Data.Pdf`（WinRT） | **不可用**：加载需 `Add-Type -AssemblyName System.Runtime.WindowsRuntime`，被本机安全策略拦截（`Add-Type` 一律 block） |

结论：**本机没有独立的 PDF 光栅化库**（不能用 Python/C 工具链那条路）。

## 1bis. 【重要更正】渲染能力其实存在——藏在浏览器里（主理人补测，2026-11-02 13:4x）

上文 §1 的结论「本机不存在任何可用的 PDF 光栅化引擎」**已被推翻**，请以本节为准。

事实链：
1. `03-code/web/assets/viewer.js` 已用 **pdf.js + canvas** 在浏览器端渲染页面（`renderPage` → `getContext('2d')`）。
2. `deepseek-harness-master/node_modules` 里有 **`playwright` / `playwright-core`**，本机 `~/AppData/Local/ms-playwright` 已装 **`chromium-1228` / `chromium_headless_shell-1228`**。
3. `dsh-impl` 的 `node_modules` 是指向 `deepseek-harness-master/node_modules` 的符号链接 → **playwright 在 dsh 侧可直接 `import` 成功**（已在 `dsh-impl/.tmp/` 内实跑验证）。

实测（headless Chromium + `03-code` 的 vendor pdf.js + 临时 HTTP 服务托管 PDF；`file://` 下 ES module 会被浏览器策略拦，必须走 HTTP）：

| 样本 | 缩放 | 编码 | 尺寸 | 体积 | 单页耗时 |
|---|---|---|---|---|---|
| 4.4（矢量页，页面内**无**整页图） | 1.5 | PNG | 892×1177 | 271 KB | 100 ms |
| 4.4 | 1.0 | PNG | 595×785 | 154 KB | 32 ms |
| 4.4 | 1.0 | JPEG q0.8 | 595×785 | **93 KB** | 23 ms |
| 4.4 | 0.75 | JPEG q0.75 | 446×588 | 55 KB | 34 ms |
| 1.17（扫描件） | 1.5 | PNG | 855×1138 | 506 KB | 113 ms |
| 1.17 | 1.0 | PNG | 570×759 | 244 KB | 31 ms |
| 1.17 | 1.0 | JPEG q0.8 | 570×759 | **98 KB** | 24 ms |

由此得到三条可直接用于设计的结论：
- **任意页都能真栅格化**，不再受「页面是否由整图构成」限制；§2 的内嵌图提取因此降级为**可选快路径**，而非唯一手段。
- **推荐默认档：scale=1.0 + JPEG q0.8**（约 95 KB / 24 ms/页），性价比最高；PNG 体积约 2–3 倍，仅在需要无损线条/文字锐利时用。
- 渲染成本可接受（单页 24–100 ms），但**每页都要过一次浏览器**，多页批量需明确上限。

## 2. 可行的替代能力（实测）

pdfjs-dist（`03-code/node_modules/pdfjs-dist` 6.4.299，纯 JS）能直接取出页面内嵌图像 XObject 的原始位图：

| 样本 | 页数 | 实测 |
|---|---|---|
| `1.17__software-agents.pdf`（扫描件，抽取被判 `needs_ocr`） | 8 | p1、p2 各有 **1 张大图**，`1579×2106`，`kind=2`(RGB_24BPP)，`data` 长度 `9,976,122` = 1579×2106×3 |
| `4.4__a-survey-...pdf`（矢量/文本型） | 42 | p1 **imgs=0**、`textChars=2232`；p2 存在图像对象 |

推论（事实层面）：页面图像**只在该页由整图构成时存在**（扫描件、部分图表页）。矢量页没有整页位图可取，
要得到它的像素必须有渲染引擎——而渲染引擎不可用。

## 3. 实现层面的两个实测坑

1. **`page.objs.get(objId)` 同步调用会抛 `Requesting object that isn't resolved yet img_p1_1`**。
   图像对象是异步解码的，必须先经 `getOperatorList()` 触发，并用回调式 `page.objs.get(id, cb)` 等待就绪。
   直接同步取值在 `4.4` 的 p2 上就会崩。
2. **`@napi-rs/canvas` 缺失会让 pdfjs 打印 3 条 polyfill 告警**（`Cannot polyfill DOMMatrix` / `Path2D`），
   并提示 `standardFontDataUrl` 未提供。取纯文本/图像不受影响，但日志会被污染，需在导入期静音（`03-code/services/extractor.js` 已有同款处理可参照）。

## 4. 依赖解析约束（关键，影响方案形态）

`dsh-impl/node_modules` 是**指向 `deepseek-harness-master/node_modules` 的符号链接**，`dsh-impl` 自身**没有 `package.json`**。
`pdfjs-dist` 只存在于 `03-code/node_modules`，不在 `dsh-impl` 可解析范围内。
因此「在 dsh 插件里 `import 'pdfjs-dist'`」当前**直接失败**（已实测 `ERR_MODULE_NOT_FOUND`）。

## 5. 模型侧已确认的能力（前置条件成立）

- `deepseek-flash` 的 Anthropic 兼容端点接受 `image` block：base64 PNG → 正确答「红色」，HTTP 200。
- `GET /models` 声明 `deepseek-flash` 的 `input_modalities: ["text","image"]`。

### 5bis. 【重要更正】图片可以出现在**工具结果**里，不必经 `agent.inject()`

上文（及早期结论）"工具输出不能回图、必须 `agent.inject()` 以用户消息注入"**是错的**，已被架构师核实、主理人复核：

- `deepseek-harness-master/packages/llm/llm-deepseek/src/images.ts:49-51`：
  `'DeepSeek Messages supports images only in user messages and tool results'` —— 即 **user 与 tool 两个 role 都允许**。
- `deepseek-harness-master/packages/fs/tool-fs/src/read-image.ts` 的 `imageReadContent()` 直接返回
  `[{ type: 'text', ... }, { type: 'image', attachment: imageRefFromValue(value.image) }]`，
  且 `read_image` 在 headless profile 里已挂载（装配探针的 `globalScopeTools` 里可见）。

由此：**无需 `agent.inject()`，无需扩 `MessageSourceMap`**；图片以 `image` block 随工具结果返回即可，
但仍需 `ctx.attachments` 服务做存储与引用（block 里是 `attachment` 引用，不是内联字节）。

## 6. 文献库现状（决定本特性的真实价值）

- 424 works / 13 PDF / 12 篇有正文；`1.17` 是唯一被判定为扫描件的（`needs_ocr`，`textPageRatio=0.125`）。
- 即：视觉通道的**直接受益面 = 扫描件与图表页**，不是「所有 PDF 都能看图」。

## 7. 扫描件文字可读性探针（主理人实跑，回应架构师 §15-1 的最大未知）

样本：`1.17__software-agents.pdf` 第 1 页（唯一被判定 `needs_ocr` 的扫描件）。
做法：playwright 渲染该页 → base64 JPEG → 发 `deepseek-flash` 的 Anthropic 兼容端点，问「照抄标题原文，看不清就说看不清，不要猜」。人工比对原图（`.tmp/shot-0.jpg`，已目视确认主标题为 **Software Agents**，顶部有栏目小字）。

| 档位 | 尺寸 | 体积 | 模型回答（节选） | 判定 |
|---|---|---|---|---|
| scale 1.0 JPEG q0.85 | 570×759 | 108 KB | `Software Agents` | **正确** |
| scale 2.0 JPEG q0.85 | 1140×1518 | 335 KB | `页面最上方那行字是：INTELLIGENT AGENTS；页面的主标题是：Software Agents` | **主标题正确**，并额外读出页眉栏目 |

结论：**扫描件正文文字是可读的**，不是「只够看版式/图表」。架构师 §15-1 关于「扫描件文字很可能读不出来」的最坏假设**不成立**（至少对本库唯一扫描件如此）。
但注意成本：scale 2.0 比 1.0 多 3 倍字节，增益仅是「顺带读到页眉」，**默认仍取低档**。

## 8. 【已更正】关于 `argsArray` 的归属：我写错了

原文此处写「Node 侧 `pdfjs-dist` 的 `getOperatorList()` 返回 `argsArray` 为 `null`，故 (b) 取内嵌位图在 Node 侧不可用」。
**该结论错误，由架构师复跑发现，主理人已独立复核确认**：

| 环境 | 实测（`1.17__software-agents.pdf` p1，pdfjs 6.4.299） |
|---|---|
| **Node 侧** `pdfjs-dist/legacy/build/pdf.mjs` | `fnArray=2639`、`argsArray=2639`，`argsArray[3] = ["img_p0_1",1579,2106]`，`objs.has()=true`，同步 `get` 直接拿到 `1579×2106 / kind=2 / 9,976,122 字节` |
| **Node 侧** `pdfjs-dist/build/pdf.mjs`（非 legacy） | 同上，同样可用（本机未复现架构师说的 `hashOrigin.toHex` 崩溃，可能与调用参数有关） |
| **浏览器端**（`03-code/web/assets/vendor/pdfjs/pdf.min.mjs`） | 我那次失败实际发生在这里：`ops.argsArray` 取不到，抛 `Cannot read properties of null (reading '0')` |

**错在哪**：我把浏览器端 vendor 版的行为，错误归到了 Node 侧。事实是 **Node 侧取内嵌位图可用**，浏览器 vendor 版那条路反而取不到。

### 但仍然存在的两条真实前提（架构师实测）
1. 必须用 **legacy 构建**（非 legacy 在部分调用下会炸 `hashOrigin.toHex is not a function`，pdfjs 自己也会警告 "Please use the legacy build"）。
2. **API 与 worker 必须同版本**：6.3.289 API + 6.4.299 worker → `UnknownErrorException: The API version "6.3.289" does not match the Worker version "6.4.299"`。本机存在两套 pdfjs，极易错配。

### 另一条 API 事实（双方实测一致）
`doc.destroy()` **不存在**（抛 `doc.destroy is not a function`），只有 `doc.cleanup()` / `loadingTask.destroy()`。

### 对 Q1 的影响
Q1 的裁决**不再依赖**本节原结论。架构师 v3 改用四条与「取位图是否可用」无关的理由（不新增运行时前提 / 契约只剩 2 个 status 且对扫描页无实际增益 / 隔离进程 / **版本一致性由结构保证**）。本节仅保留为「若将来改走 Node 侧取图，必须记住上面两条前提」。
